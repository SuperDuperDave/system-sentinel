# System Sentinel API

The one boundary. The desktop dashboard, a phone and a local agent are three clients of this interface; nothing reads the machine except through it. This document is written for an agent to read without the source. The machine-readable form is the OpenAPI document the server publishes at `/api/openapi.json`; the interactive form is `/api/docs`.

## Reaching it

The server runs on the Windows machine it reads and listens on `http://127.0.0.1:8000` unless told otherwise. Every route under `/api/` and the MCP endpoint at `/mcp` require the access token. The token is created on first start and kept in the data directory:

| Platform | Data directory |
| --- | --- |
| Windows | `%LOCALAPPDATA%\SystemSentinel\` |
| Other (development from WSL) | `~/.system-sentinel/` |

The file `token` in that directory holds it. Send it as `Authorization: Bearer <token>`. The dashboard exchanges it once for a session cookie whose value is derived from the token, never the token itself, so a browser or a phone holds something that opens the dashboard and nothing else; agents send the header. A request without a valid token gets `401` with `{"error": "unauthorized"}` and nothing else.

`system-sentinel token` prints it. `system-sentinel check` tells you whether the bridge to Windows works before you ask for anything.

The launcher signs a browser in without showing anyone the token: `GET /api/session/open?code=<one-time code>` accepts a code signed with the token, once, before the code runs out, and only for a connection made on this machine (a loopback client, or a connection accepted on the loopback listener, which is how a private-network proxy such as Tailscale serve reaches the tool). It sets the session cookie and redirects to the dashboard, or to the dashboard's sign-in link for another device with `&to=link`, the one value that lands anywhere but the dashboard itself. Agents have no use for it; they send the header.

`POST /api/session/link` is how a person already signed in hands the dashboard to a second device. It asks this machine, through the bridge, which https address Tailscale publishes for the port the request arrived on, and answers with that address, a link carrying a fresh one-time code, when that code expires, and a QR code of the link as SVG. The code lasts five minutes and is spent by the first device that follows it; the token is never in the answer. `outcome` keeps three things apart: `ok` when there is an address, `empty` when the machine answered and publishes nothing for this port (`installed` says whether Tailscale is there at all, `port` is the port it would have to publish, and `detail` names the command that would), and `unavailable` or `failed` when it could not be asked at all. `url`, `expires_at` and `qr` are null unless `ok`. It needs the session cookie or the bearer header like every other route and nothing more, because whoever is signed in may sign in another device. Agents have no use for this one either.

`POST /api/quit` stops the tool. It is the one route the session cookie does not open: it takes the bearer token, and a request carrying only the cookie is refused with `401` and a body saying the token is required, so a browser on a phone cannot shut down the machine's tool. It is also refused unless the connection came from this machine, on the same terms as `/api/session/open`. It answers `202 {"quitting": true}` and the process exits gracefully within a few seconds, under the tray launcher and under `serve`, though not under `serve --reload`, where the reloader owns the process. It is not an MCP tool: stopping the tool is not a reading of the machine, and an agent that means to stop it has the route.

### Claude Code

```
claude mcp add --transport http system-sentinel http://127.0.0.1:8000/mcp --header "Authorization: Bearer $(system-sentinel token)"
```

### Codex

```
codex mcp add system-sentinel --url http://127.0.0.1:8000/mcp --bearer-token-env-var SYSTEM_SENTINEL_TOKEN
```

Codex takes a bearer token from the environment rather than from a header, so `SYSTEM_SENTINEL_TOKEN` must hold the token in the environment Codex starts in.

### Other MCP clients

Streamable HTTP at `http://127.0.0.1:8000/mcp` with the same header. Every reading below is one tool, named as the reading is named, except that a dot becomes an underscore because MCP tool names allow only letters, digits, underscore and hyphen: `hardware.cpu` is the tool `hardware_cpu`. The stack, the composer and the captures are tools too: `stack_list`, `stack_item`, `stack_add`, `stack_update`, `stack_remove`, `stack_clear`, `stack_prompt`, `compose`, `prompts_list`, `capture_create`, `capture_list`. Every tool is annotated with what it does to the machine, so a client can stop confirming the readings and keep confirming `stack_remove` and `stack_clear`; every reading answers with typed structured content beside its text, against one shared schema for the envelope. The six presets are also MCP prompts, and the catalog and the composed handoff are resources (`sentinel://catalog`, `sentinel://handoff`). Asking for `unredacted` requires a `reason`, which is carried into the answer's warnings.

Clients that support `subscriptions/listen` can subscribe to `sentinel://handoff`. A stack change from the dashboard or an MCP tool sends a resource-updated notification; read the resource again for the new handoff. The listen request is an event stream; ordinary MCP calls still return one JSON response.

### Without MCP

`curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/api/readings/events` works from any shell. Prefer this over writing your own PowerShell: the reading carries provenance, the outcome and the redaction, and it is the same evidence the person sees.

### Exact integers across clients

Evidence uses JSON numbers for integers from `-9007199254740991` through `9007199254740991`. Integers outside that range travel as **canonical decimal strings**, for example `"134100000000000001"`, so JavaScript clients preserve every digit. This applies consistently to API responses, MCP text and structured answers, SSE frames, the CLI health reading, JSON evidence in composed handoffs and newly created capture JSON members. Booleans, floating-point measurements and existing strings keep their types; this convention does not make a floating-point measurement exact.

A large `RecordId` and every derived reference to it use the same string form. Keep it as an identifier or parse it with an arbitrary-precision integer type; do not pass it through JavaScript `Number`. Stack selections accept these decimal-string record IDs when unique within the reading; a reading spanning logs also accepts `Log:RecordId` (for example `System:42`) to identify one exact record. Machine collection, derivation, stream cursor comparisons and existing Python persistence retain exact integers. Redaction runs before this output conversion, including for sensitive numeric fields.

Existing stack evidence is converted when served or exported, without rewriting its saved file. Older capture ZIPs remain as originally written. Values already rounded by another client cannot be reconstructed; take a fresh reading when the exact value is needed. The current representation preserves exact values across clients but does not preserve a distinct JSON numeric type outside the safe range.

## The reading

Every reading is one request for evidence, returned in one envelope. Most ask Windows through the bridge; `performance_history` reads samples stored locally by the app. The envelope is the contract: a collection failure is distinguishable from no findings, and raw evidence is distinguishable from what the tool computed.

```json
{
  "reading": "events",
  "params": { "log": "System", "levels": [1, 2], "count": 50, "since": "", "before": "", "order": "newest" },
  "outcome": "ok",
  "count": 50,
  "error": null,
  "warnings": [],
  "redacted": ["host", "user"],
  "asked_at": "2026-09-20T18:04:11.204Z",
  "took_ms": 812,
  "sections": [
    { "name": "records", "class": "raw", "data": [ ... ] },
    { "name": "collection", "class": "raw", "data": { "log": "System", "outcome": "ok", "limit": 50, "returned": 50, "truncated": true, "stopped": null, "oldest_state": "ok" } },
    { "name": "coverage", "class": "derived", "data": { "log": "System", "retained_from": "2026-01-01T00:00:00.0000000Z", "covered_from": null, "covered_from_inclusive": null, "complete": null } }
  ],
  "method": { "kind": "powershell", "query": "...Get-WinEvent -FilterXml ([xml]$xml) -MaxEvents 51..." }
}
```

The verdict, error, warnings and redaction notes appear before bulk sections and the collection script in JSON text. This makes the beginning of a long answer useful to a text reader; it does not limit answer size or guarantee how an MCP client handles a large result. The same fields and values are available to structured clients regardless of order.

`took_ms` is the completed reading's wall time from entry into Sentinel's reading boundary through evidence composition. It includes Sentinel's own worker, Signals-lane and bridge-resource waits, Windows execution, parsing and local decoding. It excludes request routing before that boundary, redaction and HTTP/MCP response encoding after it. An unavailable answer still has a measured duration; it does not imply Windows was reached. `asked_at` is the host clock's timestamp when the reading envelope was constructed near the answer, not when collection began; do not subtract `took_ms` from it to infer an exact start time. Starting in v1.9.14, `took_ms` has this wall-time meaning. Earlier saved Stack readings can carry the previous mixed bridge/composition/slowest-input meanings; capture manifests identify their version, while old Stack envelopes have no version field.

**`outcome`** is one of:

| Outcome | Meaning |
| --- | --- |
| `ok` | The query ran and returned at least one record. |
| `empty` | The query ran cleanly and matched nothing in the source it could read. For event-log windows, inspect `coverage` before inferring the requested period was quiet. |
| `failed` | The query ran and Windows or PowerShell reported an error. `error` says what. |
| `unavailable` | Sentinel could not get the requested answer. A Windows bridge may be missing, unable to start, shutting down, busy or unable to finish an answer; `performance_history` may instead be unable to read its local store. The error detail says what happened. Nothing about the machine can be concluded. |
| `denied` | Windows refused (access denied, or a log that needs elevation). |
| `timeout` | The query did not finish within its limit. |

Only `ok` and `empty` say the requested source was observed. For `performance_history`, `empty` means the local store held no samples in that window; it says nothing about what the machine was doing then. Treat the other four as "not observed".

`error.kind` usually equals the outcome, but can refine it, for example with `busy`, `local_store` or an invalid response shape. `busy` with `outcome=unavailable` means Sentinel's own bridge session or WSL launch slot did not become free within the question's wait limit; this attempt could not reach Windows, so inspect the detail and retry later. Readings that ask Windows one question carry `busy` directly. Signals keeps each input's outcome and a separate `method.readings[].error_kind` when its input has a more precise cause; the warnings name busy inputs. Older saved readings that lack the refinement remain valid. `local_store` identifies a failed local performance-history read.

`record.before` and `events`/`faults.since` preserve up to seven Windows fractional timestamp digits, including the seventh 100 ns digit. `events`/`faults.before` does too and requires a time zone. The indexed Event Log XPath takes a broad millisecond interval, then an exact tick filter runs before the count cap; `collection.window_start` and `window_end` echo the exact normalized UTC bounds. A submillisecond interval is valid when its end is later than its start. `since=boot` retains Windows' rounded-down millisecond boot time. The `crash` moment and `changes` reading still use millisecond bounds. `crash`'s last-record-before-start lookup uses exact ticks independently of its moment window.

For `events`, `record` and `faults`, `collection` keeps the matching query's `outcome`, `limit`, `returned`, `truncated` flag, early `stopped` reason if Windows returned only a prefix, the resolved time boundary and the source log's enabled/mode/oldest-record metadata read after the query. The collector observes one extra matching record; that row sets `truncated` and is never returned as evidence. `truncated` is null when an interrupted query cannot establish the cutoff. An observed empty result has `{ "returned": 0, "truncated": false }`; a failed or unavailable query has no evidence sections. A failed metadata check does not erase returned records. With `since`, `events` and `faults` add derived `coverage`: `retained_from`, `covered_from`, whether that boundary is inclusive, `covered_until` and `complete`. `complete` describes the whole requested half-open interval `[since, before)`; when `before` is empty, the end is query time. A future requested end remains incomplete; `covered_until` shows the observed exclusive end, never later than the machine's pre-query time. Rows logged during the query can be later than `covered_until`. An unknown query time makes the upper reach unknown. A complete answer requires an enabled circular log whose oldest retained record strictly predates the resolved window start and a start before the machine's query time, with no response cap, early stop or unreadable or out-of-window returned time. Returned rows outside the requested interval remain visible in raw evidence and lower completeness. Without `since`, `coverage` still shows `retained_from`, while its window-completeness fields are null because no start was requested. `record` adds `coverage.reaches_before`: `true` when it returns a row before the moment or an enabled circular log's oldest record precedes that moment; `false` when it returns no rows and the oldest retained record is at or after the moment; `null` when that cannot be established. Its `truncated` flag still says whether older matching rows were left out of this response. `faults` covers Application records by report filing time, not every live kernel event that occurred. An empty match across a retention gap is a bounded finding, not proof of quiet before the boundary. Log timestamps can move backward relative to record order, and retention reach does not prove Windows emitted every event.

`events.order` and `faults.order` default to `newest`, preserving their existing answers. `order=oldest` requires an explicit `since` timestamp; `boot` is not an exact anchor for this direction. It keeps the earliest matching records in log order and includes `collection.order=oldest` and `probe_time`. When capped, the next matching record is a probe, never evidence: its time is the exclusive `coverage.covered_until`, so **later** matching records are unreturned. A stopped read reaches only to its last returned time, exclusive. The oldest-first coverage validates the independently requested window against the collector echo, readable in-window times, its host clock, probe and returned time order before claiming a contiguous interval. Unverifiable reach stays null; raw rows and, for `faults`, their decoding remain available. An unverified empty request reports failure instead of a complete absence, retaining collection and coverage diagnostics even though a failed source query itself has no evidence sections. `coverage.returned_time_ordered` states whether the returned records and probe stayed in nondecreasing time. This cannot detect a clock inversion in records the cap did not return. The default newest-first coverage retains its existing contract. For System records at or after a moment, request `events?log=System&levels=&since=<moment>&order=oldest&count=25`; the empty `levels` list means every level. Pair it with `record?before=<moment>&count=25` for the strictly earlier side. Each side has its own outcome and reach; the exact moment belongs only to the after side.

To inspect a held moment `m` in the Application log, ask `faults(since=m−1h, before=m, order=newest, count=50)` and `faults(since=m, before=m+1h, order=oldest, count=50)`. Pass the **same exact zoned `m`** as both bounds; a record at `m` belongs only to the second side. Read each outcome, collection and coverage independently and keep both raw record arrays. These are filing-time views, not proof of when a fault occurred. A live-kernel report may have records on both sides, so a grouped decoded report contains only records returned on that side. The Record view uses these two reads on first opening nearby fault reports, without a background poll; the outer hour bounds use browser milliseconds while the shared moment keeps its seventh digit. Oldest-first cost on a large retained Application log, especially for a recent moment, is not established by the sparse host probe.

`whea` has two independent event-log sources: its `collection.sources` keeps each one's outcome, cap, stop and retention metadata even when the other source fails. It asks each for one extra record, then returns the newest `count` across both. Its top-level `collection.truncated` is true when the merge discarded returned rows or either source hit its cap; false does not establish completeness if a source failed or stopped, so read `coverage` and the per-source outcomes. Numeric minimum and maximum values in the catalog and MCP tool schemas are enforced before PowerShell runs. In JSON tool calls, explicit `null` for an optional parameter uses its published default; send `levels: []` to request every event level. In URL queries, omit a parameter to use its default. An ISO timestamp with an explicit offset or `Z` is safest across WSL and Windows; an offset-free input is interpreted in the server's local zone. `boot` uses Windows' reported kernel-session start, which can span power-ons with Fast Startup.

`whea_window` asks one selected WHEA log for bounded previews in the exact half-open filing-time interval `[since,before)`. Both times require `Z` or an offset and accept up to seven fractional digits; the response normalizes them to UTC without rounding. The source first takes its own pre-query clock and can observe only up to that instant. A broad millisecond XPath filter uses the log index; a full-tick PowerShell filter removes outside rows **before** the count cap. `order=newest` keeps the newest side, `order=oldest` the oldest side; the returned `records` are always ascending by filing time. The extra matching probe row is not returned but its time qualifies `coverage`: a capped newest read has an exclusive `covered_from`, and a capped oldest read has an exclusive `covered_until`. A stopped query uses the last returned time on its requested side. These directional reach fields assume event times did not move backward across retained record order. The tool detects inversions among returned rows and the probe, but cannot detect one among unreturned rows; a clock correction could invalidate a claimed reach. `complete=true` requires a clean uncapped query, returned times in log order, an enabled circular log whose oldest retained row precedes `since`, and `before` no later than the pre-query clock. It describes retained reports the log had received by then, never an error-occurrence timeline or a claim that Windows emitted every event. An `empty` future window is incomplete; a failed or denied source has no evidence sections. The window has no cross-log groups or message signature. Take `whea_record` and compare `TimeCreated` before relying on an exact row. Selection is required, so bulk capture omits this reading.

To inspect a held moment `m` in one WHEA log, ask two independent `whea_window` readings: `since=m−1h, before=m, order=newest` for the nearest reports before it, and `since=m, before=m+1h, order=oldest` for the earliest reports at or after it. Pass the **same exact zoned `m`** as the first exclusive end and second inclusive start; a report timestamped exactly `m` appears only on the second side. Read each envelope's `outcome`, `collection` and `coverage` separately. If a side reaches its count cap, `newest` leaves earlier reports unreturned and has an exclusive `covered_from`, while `oldest` leaves later reports unreturned and has an exclusive `covered_until`. Both are report-filing-time views, not evidence that an underlying error occurred at `m`. The Record view uses this recipe with 250 preview slots per side when someone opens nearby hardware reports; its outer hour bounds are rounded to browser millisecond precision while the shared moment retains its exact seventh digit.


A collector that returns one structured object must actually return exactly one object. Missing, scalar or multiple-object output yields `failed`, a null count and no evidence sections; the adapter never chooses the first of several answers or substitutes an empty object. An object containing legitimately empty collections remains valid, and the reading determines its outcome from those collections. List collectors can still return observed empty lists or multiple rows.

**`sections[].class`** is one of:

| Class | Meaning |
| --- | --- |
| `raw` | Fields returned by the reading's source, usually Windows, sometimes projected and bounded by the reading; `performance_history` returns exact local sample rows. Default redaction applies. |
| `derived` | Computed from raw by a stated rule (a count, a bucket, a signature, a decoded structure). The section names its inputs and rule in `basis`. |
| `invariant` | A fact established as stable across readings; do not use for a current inventory that can change. |
| `inferred` | A lead: a pattern the tool noticed that a person or an agent should investigate. Never a diagnosis. `basis` names the rule. |

**`method`** is how the reading was taken: a bridge and query text, or a local source for stored history. A reading built from several queries lists them.

**`warnings`** name partial work inside an otherwise observed reading: a Windows sub-query that failed, truncated returned rows, or a malformed stored sample that was skipped.

**`redacted`** lists what the default redaction removed from this response. By default recognized serial and identity fields, computer and user names, MAC addresses, network addresses (IP, gateway, DNS), and user-profile path segments are masked. Fields are redacted by name wherever they appear, and the machine's own names are replaced inside text once learned. If a native Windows identity query fails, the server can use its inherited `COMPUTERNAME` and `USERNAME` while still reporting the bridge failure; a later failed query does not erase names already learned. CPER binary strings are withheld by content wherever they appear: the fixed `HeaderHex` in a `whea` or `whea_window` preview, and `RawData` plus its copy in `Properties` in `whea_record`; `redacted` then includes `cper`. Header severity, record identity and previous-session facts are still derived from the original bytes before redaction. Pass `?unredacted=true` (or the `unredacted` argument in MCP) to receive the bytes that reading actually collected; use `whea_record` for full CPER bytes and exact Windows fields. The Hardware errors screen offers this exact readout on demand. Message text is kept where the reading collects it, so an unknown identifier inside free text or an unrecognized binary format is not guaranteed to be removed. Device instance identifiers are kept in the existing hardware readings to tell PCIe endpoints apart; `changes` excludes them and full event messages from its Kernel-PnP projection because those values can contain a serial.

If no host name is known and an identity lookup is due, redacted HTTP and MCP callers wait for one shared lookup. A routine unavailable lookup retains the previous policy and is retried no more than once a minute. An unexpected lookup exception refuses redacted answers until the next attempt or a successful identity learn; edits that need that policy are refused before their saved data changes. A connected live event stream closes in that interval and a client may reconnect after recovery. Explicitly requested unredacted answers still follow their existing authorization and reason rules.

## The catalog

`GET /api/readings` lists every reading with its description, classes, parameters and their defaults, fields or content that may contain details affected by default redaction, whether it is heavy, and whether it requires an exact selection. The catalog's `private` list is a cue to inspect the response's `redacted` list; it does not mean every listed field is removed. For paths, default redaction masks recognized user-profile segments while retaining the rest of the path. Beside the list is a `version`: the tool's own, which is how a caller tells what is answering. The live catalog is authoritative; this is the catalog as designed, with each reading's sections.

| `events` | Records from a Windows log by level, and from a moment or Windows' reported kernel-session start | `records` (raw), `collection` (raw query and retention), `coverage` (derived retained reach and window completeness when requested) | `log` (System, Application), `levels` (1 critical, 2 error, 3 warning, 4 information; `[]` means every level; default 1,2), `count` (default 50, 1 to 2000), `since` (an ISO timestamp or the word `boot`; empty for the most recent records), `before` (exclusive ISO end with `Z` or offset; empty for query time), `order` (`newest` default or `oldest`; oldest requires an explicit ISO `since`, not `boot`) |

For `whea`, `coverage.complete` means every matching row the two logs **currently retain** was previewed; it says nothing about older events those logs rotated away. `coverage.cutoff` is the exclusive time after which the answered sources are fully shown when a count limit or stopped query leaves an older tail; rows at that exact time may be missing. A failed source keeps completeness false even if the other source returned rows. The CPER `previous_session` flag means the error occurred in an earlier Windows session, so that event's `TimeCreated` is a later report time, not the stop moment. `groups` marks only unambiguous cross-log pairs with matching, nonzero CPER identifiers and supporting fixed-header bytes as likely repeat reports; both source previews remain in `records`. Use `Log:RecordId` to select one for an agent handoff, because event RecordIds can collide across logs. A selected preview Stack handoff carries its bounded row, fixed-header identity and source coverage. Take `whea_record` and compare `TimeCreated` for exact raw and decoded detail before making an exact-record handoff. A large reading's summary keeps header severity and previous-session status beside bounded record excerpts, with the full stored preview available on demand.

For `whea` and `whea_record`, `identity.cper.header_time` replaces the older `identity.cper.timestamp` field; saved older Stack readings retain their original shape. The preview reads only a fixed header and declared payload length; `whea_record` checks the full CPER structure before deriving the same fields. `header_time` is null unless the CPER timestamp-valid bit is set. Otherwise it preserves the eight `bytes` as stored, the independent `precise` and `reserved_bits` flags, and two conditional parses, `as_integers` and `as_bcd`, each requiring valid calendar fields including a year within its century. `reading` names one only when exactly one parse is valid; `both` means both produce the same date, and null means either both differ or neither forms a date. It does **not** certify which encoding the record creator used. The [UEFI CPER format](https://uefi.org/specs/UEFI/2.11/Apx_N_Common_Platform_Error_Record.html#record-header) specifies local BCD collection time; Microsoft's [Windows WHEA timestamp structure](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_whea_timestamp) describes the same fields and precise bit but does not state an encoding or time zone. A set precise bit is the record's claim that its time correlates to the error event. The tool assigns no time zone and never places this header time on a report timeline. `TimeCreated` is the separate Windows event filing time.

`whea_reports` queries the Kernel-WHEA channel independently with a 20,000-row cap plus one probe row. Its counts are **reports**, not unique hardware errors or a measured occurrence rate; `whea.groups` is the place to inspect likely repeat reports across the two logs. The query carries only the first 128 CPER bytes across the Windows bridge to interpret fixed header flags. Per-report `reports` references, which omit those bytes, require `references=true`; they include returned reports whose filing time cannot be placed. A short, missing or inconsistent header has an explicit reason and leaves PreviousError unknown. Use `whea_window` with `source=kernel_whea`, `since=bucket start` and `before=bucket end` for up to 500 previews of a selected exact interval, then `whea_record` with the report's `record_id` to retrieve the exact retained event, including its CPER bytes on an explicit unredacted request. A zero bucket is only an observed quiet **report** interval when the channel's retention and bounded query cover it; null means no such claim is supported.

The broad `storms` and `whea_reports` timelines keep `buckets.totals` at every bucket index: a number is covered, `null` is unknown. `buckets.returned` has parallel `index`, `count`, `previous_session` and `header_unreadable` arrays only for buckets with placed reports, including those where `totals[index]` is unknown. A bucket starts at `buckets.from + index × bucket_seconds`; its full coverage is `totals[index] !== null`. `storms.buckets.signature_pairs` has parallel `index`, `signature` and `count` arrays; `signature` is the position in that answer's `signatures` list. A pair counts placed reports only. Both readings' `buckets.severity` counts returned reports, including unplaced ones, under `fatal`, `recoverable`, `corrected`, `informational`, `unknown` (a readable unrecognized code) and `unreadable` (no readable fixed header). Older saved Stack items can still contain the former `active` object list. The default timeline omits per-report references; set `references=true` only when that full returned list is needed.

Pass `before` to place a `whea_reports` window around an older report or restart without spending the cap on later traffic. It requires an explicit time zone, is rounded down to the millisecond, and is exclusive. `collection.window_start` is bucket-aligned; `window_end` is the actual exclusive end, and `queried_at` comes from the host clock. Because the bucket start is aligned to wall-clock boundaries, it can begin up to one bucket after `before − hours`; inspect the actual bounds before treating them as the requested interval. An end beyond the host clock shifts the observed window earlier at both ends, is warned about, and cannot make `coverage.complete` true for the requested interval; a requested interval entirely in the future fails. `coverage.covered_until` gives the observed end. A window ending at a restart cannot include a previous-session report filed after it. The Record moment frame uses two directional `whea_window` previews meeting at its held moment, each with its own reach; it opens one exact `whea_record` in place.

`reliability.collection` identifies the inclusive query window as `window_start` and `window_end`, and reports `records` and `stability` independently. Each source has `outcome` (`ok`, `empty`, `denied` or `failed`), `available` (matching rows before the response limit, or null when unobserved), `returned`, `limit` and `error`. The envelope is `empty` only when both sources answered without history. If no history is available and either source failed, the envelope is unobserved; useful data from a surviving source remains `ok` with warnings. When the event source failed, the envelope's `count`, the daily `records` and `event_types`, and the aggregate `sources` are null. The stability index remains usable, and any index-fall signal preserves those unknown event counts. Counts describe returned rows; compare `available` with `returned` to see whether the event list was limited.

`changes` uses the interval `[before − hours, before)`, or the Windows host's current time when `before` is empty. The end is rounded down to the millisecond that Windows Event Log XPath compares. `collection.window_start`/`window_end` keep the raw bounds the collector reported; the reading independently compares them with the requested millisecond interval before claiming coverage. A mismatch leaves coverage unknown, while safe rows remain visible and are classified against the requested interval. Each derived change has `outside_window` true, false, or null when a live window cannot be verified. Three service-filtered event-log queries answer independently: Windows Update 19 is an installation success and 20 a failed attempt; Kernel-PnP 400 is device configuration, which does **not** establish a driver update; MSI 1033/1034 are installation/removal results, whose status distinguishes success from failure; status 1641 means a restart was initiated and 3010 means one is required. MSI does not cover every installer or Store app. The raw `records` section retains each event's log, RecordId, timestamp, provider, ID, version and only fields the reading can project safely. `FieldCount` and `OmittedFieldCount` make its projection limit explicit. It omits messages and device instance identifiers from the Configuration log, because those can include serials. `changes` derives one labeled timeline entry per returned record and cites `{log, record_id}`; an unsupported layout keeps its projected raw row and an entry error. No event's proximity to a crash establishes a cause. [Microsoft's Windows Installer event reference](https://learn.microsoft.com/en-us/windows/win32/msi/event-logging) documents the MSI field positions; its [Windows Update troubleshooting example](https://learn.microsoft.com/en-us/troubleshoot/windows-server/installing-updates-features-roles/troubleshoot-windows-update-error-0x80070002) shows event 20 as a failed installation.

`changes.collection` gives `windows_update`, `device_configuration` and `msi` separate outcomes, returned counts, per-source limits and exact `truncated` flags. Each source also says whether its log was enabled, its mode and oldest retained record when readable. The derived `changes.coverage` section gives each source a `covered_from` boundary, `covered_until` and `complete` (`true`, `false`, or null when unobserved). `covered_from` is the earliest supported boundary in the requested interval, accounting for retained history and any response truncation; it is null when log state or retention cannot support that bound. `covered_from_inclusive` is false at the oldest retained or oldest returned timestamp, because earlier records may share that time; it is null when the boundary is unknown. `covered_until` is the observed exclusive end, capped at the machine's pre-query time. `complete` requires an observed query, an enabled circular log with a retained record before the requested start, no returned-record truncation, and an end the machine has reached. A future requested end cannot be complete. A projected row outside the requested interval remains in raw and derived evidence, is counted in `collection.row_issues.outside_window`, and prevents completeness. This is a bound on the **retained log** assuming timestamps have not moved backward across record order, not proof that Windows emitted every relevant event. A source that failed is never an observed empty source. The envelope is `ok` with partial-source warnings when at least one validated record falls inside the requested interval, `empty` only when all three queries answered without records, the interval and host query time were verified, and the interval began before the host query time, and otherwise `failed` or `denied` with a null count. Its count covers only in-window rows; outside rows stay in raw and derived sections, and the summary still counts all returned rows. Even an `empty` reading can have a retention warning: inspect `coverage` before treating the whole requested interval as quiet.

`storms` reports the System WHEA-Logger query, its exact one-extra-record truncation result, an early stop when one occurred, and the log's enabled/mode/oldest evidence in `collection`. The Windows clock supplies both query bounds and bucket alignment. When a query stops after returning records, validated in-window records remain visible, while the boundary at the oldest returned record is exclusive and older time is unknown. `collection.system.returned` counts rows sent by Windows; its `outcome` describes the query before the narrow window-boundary filter. The envelope's `outcome` and `count` describe counted in-window events, including events whose projected time could not be read. Thus the query can say `ok` while the reading says `empty` if its only returned row lay just outside the requested boundary. If that happens during an interrupted query, the normalized source says `failed` or `denied` because no in-window event could be counted. `collection.system.row_issues` counts unreadable times and rows within one millisecond of, but outside, a query boundary; the latter are not counted or retained. A row further outside the window or a broken projected shape fails the source. In `buckets.totals`, `0` means that bucket was observed without a matching event; `null` means coverage of the whole bucket could not be established from retention, the response cap, an interrupted query or an unplaceable event. An unplaceable event makes every bucket unknown, while `buckets.returned` and `signatures` still retain placed events. A burst can be established from returned placed events even when surrounding time is unknown. Acceleration needs an observed recent and baseline window; quiet needs the whole requested window covered. Otherwise `status.state` is `unknown` and its rates are null where they cannot be calculated. The final bucket is only observed through `collection.window_end`, a millisecond-aligned host query time. A clean empty event query can therefore coexist with an unknown storm status. The Hardware errors trace shades buckets of unknown coverage and keeps returned event stretches available to inspect.

The System collector projects at most the first 128 bytes of each returned event's first binary property. A shared fixed CPER-header reader derives the PreviousError flag; the projected bytes are omitted from the reading. `buckets.previous_session` and `buckets.header_unreadable` count all returned in-window reports, even with unplaceable filing time; `header_unreadable_reasons` distinguishes missing, short and invalid headers. Sparse returned-bucket and signature counts require a placed filing time. `status.state` remains a lead about **all** System report traffic. The separate `status.not_marked_burst` is `true` if enough reports with a readable header *not marked* PreviousError share a recent bucket; `false` only if complete recent buckets show that even unreadable headers cannot reach the threshold; otherwise it is `null`. `not_marked_peak.at_least` counts observed unmarked reports in the busiest recent bucket; `at_most` includes unreadable headers and is null when recent coverage is incomplete. A clear PreviousError bit does not establish when the underlying error occurred. Old saved readings have no header counts or this lead; do not interpret those absent fields as zero or false.

Pass `before` to inspect an older System WHEA-Logger filing-time window without later traffic consuming its 20,000-row cap. The end requires a time zone, is rounded down to a millisecond, and is exclusive. `collection.window_start` is bucket-aligned; `collection.window_end` is the actual observed end; `collection.queried_at` is the host query clock. Bucket alignment can place the start up to one bucket after `before − hours`. `coverage.system.covered_until` identifies the observed exclusive end. An end beyond the host clock moves the observed window earlier, warns, and cannot be complete; an interval wholly in the future fails. A historical answer retains buckets, signatures, collection, and coverage, including fixed-header counts, but omits `status`: live burst, acceleration, and quiet thresholds do not describe the current machine from a past window. These are Windows filing times; a cluster after restart can include reports of earlier errors. To inspect individual reports, ask for `references=true` in a narrow window. The optional `reports` section then carries one row per returned in-window report: `record_id` (nullable), `reported_at` (nullable), `event_id`, `signature_id` (null when its time could not be placed), `header` and `header_error`. The references follow collector order and include unplaced reports. Their count equals `buckets.total + buckets.unplaced`; only placed rows join `signatures`. No message or CPER bytes enter these references. At the 20,000-row cap, this section can add several megabytes to an API or MCP answer. For an exact retained event, take `whea_record` with `source=system` and a non-null `record_id`, then compare its `TimeCreated` with `reported_at` because a log-local ID can be reused. A reference without a readable filing time cannot confirm that identity by time. `whea_reports` reads the separate Kernel-WHEA channel.

`GET /api/readings/{name}` takes the reading. Parameters are query parameters; a name the reading does not take is refused with `422` rather than ignored, so a misspelled parameter cannot read the wrong evidence with a clean outcome. Heavy readings (`changes`, `dump_header`, `hardware.*`, `pcie`, `power`, `memory`, `reliability`, `signals`, `load`, `processes`) are loaded on demand; `changes` is currently available through the API and MCP without a dashboard view. `processes` runs on opening Performance and while it remains open; `load` runs only when the fresh-snapshot button is pressed.

The app samples `load` in the background by default at 60-second intervals whether a dashboard is open or not. `GET /api/performance/collection` reports `settings` (`enabled`, `interval_seconds`, `config_error`), `last_attempt` (`at`, `outcome`, `took_ms`) and `retention_days`. `PUT /api/performance/collection` accepts `{"enabled": false, "interval_seconds": 60}` to pause; set `enabled` true to resume and choose an interval from 60 to 600 seconds. `DELETE /api/performance/history` removes all retained sample day files and resets the last-attempt status without changing the enabled setting. All three routes require the same authentication as readings. Stored rows under the local data directory's `performance/` folder are JSONL with UTC timestamps and numeric fields only, bounded to 30 calendar days and 512 KB per day. A malformed line is skipped with a reading warning; failure to read the store gives `unavailable`, not an empty history. No sampling data is uploaded.

`processes` is requested when the Performance view opens and refreshes once per minute while it stays open. It is never part of the background JSONL collector. Its `cpu_core_percent` is Windows' Process counter on a one-processor scale: 100% is one logical processor, and a multithreaded process can exceed 100%. Where Windows returned a logical processor count, `leaders.cpu[].logical_capacity_percent` divides by that count as a separately labeled estimate. `private_working_set_bytes` is resident memory private to the process; `private_bytes` is a different committed counter. `io_bytes_per_sec` is process I/O, which can include activity beyond disks. The counter instance name can carry a `#` suffix; PID distinguishes simultaneous instances but can be reused after exit. The reading does not ask for executable paths or command lines. If the response limit is reached, the script preserves high users in all three ranking dimensions and reports omitted rows; rankings never claim to describe those omitted processes. Microsoft documents the [formatted WMI counters](https://learn.microsoft.com/en-us/windows/win32/wmisdk/accessing-wmi-preinstalled-performance-classes) and [multi-processor Process counter](https://learn.microsoft.com/en-us/windows/win32/perfctrs/collecting-performance-data).

`dumps` checks Minidump, MEMORY.DMP and LiveKernelReports under Windows' actual `SystemRoot`. Each `collection.locations` entry names its path, recursion, `present` (boolean or unknown), `outcome`, returned file count and bounded error details; `error_count` preserves the full error count when only the first 20 details are returned. `collection.complete` means all locations answered. A missing location is an observed empty result; a denied or failed directory walk keeps any files already returned. Useful files yield `ok` with warnings when coverage is incomplete. With no files, a collection failure yields `failed` or `denied` with a null count; only a complete empty inventory yields `empty`. This coverage also appears at `crash.collection.dumps`, without changing the outcome of its primary event-log queries. Each stop carries `dump_inventory_complete`, qualifying a missing match or the newest returned time candidate when some locations could not be read. An unmatched reported dump path carries `inventory.outcome` and `inventory.detail`: whether its location could be checked, or whether a current file exists but was not matched to that historical stop.

`dumps` also searches the default current Windows process user's `LocalApplicationData\CrashDumps` directory, directly and without recursion, as location `application`. File rows retain `name`, `path`, `bytes` and `modified`, with `source` naming the inventory location. This does not discover custom WER destinations, other accounts, service profiles or WER archives, and it does not enable dump recording. Windows documents the [default and configurable user-mode dump locations](https://learn.microsoft.com/en-us/windows/win32/wer/collecting-user-mode-dumps). Application files are excluded from `crash`'s kernel-only inventory and stop matching.

The application source resolves its folder without creating or verifying it first, checks for a canonical fixed-drive path, and checks ancestors and candidates for reparse points before following them. Unsupported or redirected locations are collection failures, not observed empty directories; ordinary files found beside rejected entries remain available with incomplete coverage. These pathname checks are not an adversarial filesystem sandbox: concurrent changes, DOS aliases and hard links are not excluded by the policy. The same guard runs again before opening an application file.

**Selecting a dump with privacy preserved.** The shared API/MCP service adds derived `inspection_targets` to `dumps`: each target has `file_index` (zero-based position in the returned raw `files` array), `source`, and an opaque `ref`. Use `dump_header(ref=...)` even when the displayed path or filename was redacted. References are keyed to the running service instance and reveal no path; no key enters a query, capture or response. They select the **current file at that location**, not saved bytes or an immutable version. They remain stable within the instance; after restart or an unknown reference, refresh `dumps` and select again. Historical stack/capture evidence remains readable after its reference expires.

Malformed references, another instance's reference, both selectors or neither selector are request errors. A valid reference is resolved against a fresh inventory; the header collector then checks its own fresh inventory before opening. Both queries and their combined bridge time are returned. A missing match under an observed source yields `empty`; an unreadable requested source yields `denied` or `failed`. Unrelated source failures stay warnings. A file may change or disappear between queries. Direct unredacted `path` calls remain supported; passing a redacted placeholder is refused with instructions to use a reference. Standalone collectors and benchmarks retain direct-path access; session references belong to the shared service used by API, MCP, stack reads and captures.

`dump_header` opens only a file already found in the Windows dump inventory. It reads the first 96 bytes and returns them in hex with the offsets of interpreted fields. `PAGE`/`DU64` yields the recorded 64-bit kernel bug check and parameters. `MDMP` yields its 32-byte header and up to 128 directory entries (1,536 bytes), plus bounded fixed exception and system metadata, a thread count and up to 128 module records with at most 512 UTF-16 bytes per module name. Every sampled fixed record and its file offset is in the raw sections; module names are returned as text so the normal path redaction applies. The derived `inspection` names the exception, system and any loaded module range containing the exception address. A range match locates code; it does not establish a cause. The Crashes detail shows the interpretation first, with the raw readout in place; a stacked dump starts with the interpretation and keeps the raw sections available when expanded to full. Directory entries that point outside the file, a changing file, a zero-byte file, a missing sample and a directory over the limit are reported explicitly. The raw `collection` preserves the inventory coverage on both successful and unsuccessful inspections. `empty` means no exact match was returned and the requested location was observed (or the path lies outside the inventory scope). If that location could not be fully read, the inspection returns `denied` or `failed` and file presence remains unknown. An unrelated location failure does not hide an observed missing match. Windows may also list a file but deny opening it. Inventory matching is case-insensitive and exact; path normalization is used only to classify coverage, never to authorize opening a file. A normal process may encounter denial under `C:\Windows\Minidump`. This structural read does **not** validate the whole file, unwind a stack, read module contents or memory streams, or identify a cause. No debugger runs and no symbols are fetched. Microsoft documents the [DUMP_HEADER64 fields](https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/System/Diagnostics/Debug/struct.DUMP_HEADER64.html), [MINIDUMP_HEADER](https://learn.microsoft.com/en-us/windows/win32/api/minidumpapiset/ns-minidumpapiset-minidump_header), [stream directory](https://learn.microsoft.com/en-us/windows/win32/api/minidumpapiset/ns-minidumpapiset-minidump_directory), [module list](https://learn.microsoft.com/en-us/windows/win32/api/minidumpapiset/ns-minidumpapiset-minidump_module_list), and [DumpChk's fuller validation](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/dumpchk).

Full records from a log (`events`, `record`, `whea_record`, `crash`, `faults`, the stream) share one shape: `RecordId`, `Id`, `Level`, `LevelDisplayName`, `ProviderName`, `ProviderId` (canonical GUID text or null), `Version` (integer or null), `MachineName`, `TaskDisplayName`, `TimeCreated` (UTC, ISO), `Message`, `Properties` (the event's data, binary values as hex). The `whea` and `whea_window` previews carry the smaller shape named in their catalog rows above. `whea_record`, `crash` and `faults` also carry `Log` to identify a selected or combined source; the readings that ask only one ordinary log do not.

### Application process interpretation

Application Error 1000 and Application Hang 1002 decoded entries include `process`: nullable `id` and `created_at`, exact decimal `creation_filetime`, `creation_resolution_ns`, independent `id_status`/`creation_status` and reasons, `source`, and `warnings`. Status is `ok`, `absent`, `malformed` or `unsupported`. A bad start value cannot erase a valid PID, and a bad PID cannot erase a valid start. The original properties and existing named fields remain available.

Normalization requires the supported provider GUID, integer event ID and version, and a property array with the exact supported count:

| Provider | GUID | Event / version | Properties | PID / creation field |
| --- | --- | --- | --- | --- |
| Application Error | `a0e9b465-b939-57d7-b27d-95d8e925ff57` | 1000 / 0 | 15 | `ProcessId` / `ProcessCreationTime` |
| Application Hang | `c631c3dc-c676-59e4-2db3-5c0af00f9675` | 1002 / 0 | 10 | `ProcessId` / `StartTime` |

`source` retains the record's provider/event/version and, for a supported layout, each field's name and zero-based property index, plus the creation encoding and its interpretation basis. Missing historical metadata, another version or a shorter/appended layout gives unsupported process facts. This bounded mapping trusts the publisher's layout identity; it does not detect same-count reordering under an unchanged identity, authenticate the record or query a provider template on every reading.

Start values are interpreted using Windows [process creation FILETIME](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes): units of 100 nanoseconds since 1601 UTC. The supported Error message names the application start; Hang's message does not describe its `StartTime`, so its per-entry basis states the weaker support. `created_at` preserves seven fractional digits using integer arithmetic. `creation_resolution_ns: 100` describes the encoding, **not clock accuracy**. These are interpreted process facts, not proof that a file belongs to a particular fault; PID reuse and dump timestamp precision still matter.

Exact integers, canonical unsigned decimal strings and explicit `0x` hexadecimal strings are accepted. Booleans, floats, negative values, ambiguous bare hex and values outside their unsigned 32/64-bit range are refused. Null/empty values are absent. A zero PID/start is unsupported with an explicit reason; no undocumented sentinel meaning or 1601 creation date is asserted. Valid ticks outside the supported calendar range retain `creation_filetime` while the date remains unsupported. A start later than a valid event timestamp is kept with a warning, since clock changes or the source values can need investigation. Hang `TerminationTime` remains an uninterpreted raw value.

### Minidump process metadata

For `MDMP` stream 15, Sentinel reads only the 24-byte common prefix of [MINIDUMP_MISC_INFO](https://learn.microsoft.com/en-us/windows/win32/api/minidumpapiset/ns-minidumpapiset-minidump_misc_info), including larger versions of the structure. The full declared stream must fit within the file, and `SizeOfInfo` must be between 24 and the directory entry's declared size. Raw `streams.entries[].misc_info` retains the six integer fields, their file offsets and field-use flags beside the exact sample bytes. `inspection.process` is null if no valid record was read; otherwise it contains nullable `id`, `created_at` (UTC) and `creation_precision_seconds`. Flag `0x1` permits the process ID; flag `0x2` permits process creation time and CPU times. Unused bytes never become process facts. A valid creation time has one-second precision; its exact epoch-seconds value and the user/kernel CPU seconds remain in the raw metadata. These recorded values can support comparison with other evidence, but PID reuse and timestamp precision prevent treating the pair as an authenticated or unique process identity. No automatic fault association is performed.

For `MDMP`, the raw `streams.entries` list includes every directory entry even when its fixed metadata was not sampled. A later stream of a type already sampled has `sample_status: skipped_duplicate`; that planned limit is distinct from an unavailable or incomplete read. Crashes presents this list with each declared range and read status before the exact raw file readout.

## The moment

"It froze at 02:14." The log does not announce a freeze; the next start does, and the facts that name one stop are spread over four records in two logs and a file on disk.

`crash` is the call to reach for first. It fetches them in one launch and composes one stop per session: when the machine stopped as Windows estimated it (read from EventLog 6008's binary value, not from its locale text), when it started again, the bug check if one was written, the dump on disk that belongs to it and how it was matched, and the last System record before that start. The record may be later than the estimated stop time; it supplies context but does not by itself establish cause. Given `moment`, it reports what the first start at or after that moment announced **when the System log still reaches before the moment**. A clean-start `empty` answer also requires Application report retention to reach before that start and both primary queries to be complete. If the first start cannot be established or classified, the warning names the gap and returned stops and reports remain available. A report-only stop is ordered by its filing time; the actual stop came earlier and may predate the requested moment.

The raw `crash.collection` section reports the primary `system` and `reports` queries independently: `outcome` (`ok`, `empty`, `denied`, `failed`), `returned`, `limit`, `bound_reached`, `error` and the log's enabled state, mode, oldest retained record and metadata-probe status. A reached bound means the result may be incomplete; no total matching count is claimed. For an unobserved query, `returned` is zero and `bound_reached` is null. A metadata-probe failure does not erase records or change the primary query outcome. The derived `coverage` section gives each log's `retained_from` and `reaches_moment` (`true`, `false`, or `null` when reach is unknown), plus `first_start` (`at`, `started_at`, `record_id`, `established`; null without `moment`). `at` is when the Kernel-General 12 record was written, while `started_at` is its reported boot time and may precede the record by seconds. The log query uses the supplied moment normalized to UTC milliseconds, rounding down any finer fraction; retention reach is compared with that same boundary. `established: true` with `at: null` means no start record was returned from an uncapped, retained System window. A retained record exactly at the query boundary is insufficient to prove reach. An envelope with surviving stops is `ok` with warnings for failed sources. With no stops, either primary query failing makes the envelope unobserved with `count: null`; `empty` requires both queries to have answered, within their stated bounds. `collection.before` records each attempted supporting lookup by `anchor` RecordId and `at` timestamp, with its outcome, returned count and error. Those lookup failures preserve the primary stop evidence. This section covers the event-log queries; it does not certify dump-inventory completeness.

Each stop carries: `started_at` (the start that announced it), `announced_at` (the Kernel-Power 41), `stopped_at` (Windows' own estimate, from the 6008), `reported_at` (when Windows Error Reporting filed the report, including a report without a returned System session), `down_seconds`, `bugcheck` (`code`, `name` or null when the table does not know it, `parameters`, `source`: which record named it, `bucket`: the failing module when WER analysed the dump), `no_bugcheck_recorded` (true only for code 0 with no bug check in complete primary queries and Application retention reaching before the stop; null when query or retention gaps prevent that absence finding), `power` (the 41's fields that say what kind of stop it was), `dump` (`name`, `path`, `bytes`, `modified`, `matched_by`: `1001`, `report` or `time`; a file not returned by inventory keeps its reported path and loses its size), `last_record_before` (the last System record before a returned next start, including the first line of its message) with `quiet_seconds` (time from that record to the next start), `last_record_collection` (the matching supporting query result, `outcome: not_requested` when no start was returned, or `not_returned` when an expected lookup result is missing), and `records`: the record ids the stop was composed from, for the stack. A 41 without a returned start does not anchor a pre-start lookup: the preceding record might already be from the new boot. The independent log boundaries help explain a report without a System session; a report timestamp alone does not establish when its stop occurred.

Then `record` with `before` set to that stop's `started_at` returns System records before the next start, oldest first — the same mechanism the dashboard offers as *The record before this*. Inspect their timestamps against the stop estimate before drawing a conclusion. `faults` can query reports filed around the stop; `whea_reports` and `storms` can independently query their respective WHEA logs by filing time around the next start. `whea` is a newest-record sample. An anchored storm window shows traffic and coverage but no live urgency status, and neither WHEA log's filing time alone establishes when the underlying error occurred. `signals` says what the tool noticed across its own observation window.

## The stream

`GET /api/stream` is server-sent events, polled from the logs every few seconds with one query per poll.

| Event | Data |
| --- | --- |
| `record` | `{ "log": "System", "record": { ...the record shape... } }` for each new record matching the tool's presets: crash and power (Kernel-Power 41, EventLog 6008, WER 1001, volmgr 46, disk 161 and 162), WHEA (1, 17 to 20, 46, 47), storage (7, 11, 51, 55, 57, 129, 153), driver and service (219, 7000 to 7034, 10110, 10111), application crashes (1000 to 1002), TPM (1796, 1801) |
| `heartbeat` | `{ "at": "...", "cursors": { "System": 307379, "Application": 88120 } }` on every poll |
| `bridge` | `{ "outcome": "failed", "error": "..." }` when a poll did not observe the machine, with the reading vocabulary |

A silent stream is not a healthy machine; a stream with heartbeats and no `bridge` events is. Records arrive redacted unless the stream was opened with `?unredacted=true`. A connected stream uses the current identity policy for each poll, including one learned after the connection opened. While the machine is not answering, the poll backs off to every twenty seconds and says so with a `bridge` event each time.

Each connected client starts at the logs' current cursors and polls independently. Reconnecting starts at the current cursors; records missed while disconnected are not replayed. A disconnected client can also lose records fetched but not yet yielded. `health` reports process-lifetime `bridge.questions` (`asked`, final `busy` answers, current `in_flight`, peak `in_flight_max`) and `streams` (current and peak `connected`, cursor and poll `asked`, raw `records_returned`, `polls_at_limit`). A bridge retry counts as one question, and a stream cursor request counts as one stream ask. `records_returned` counts items returned by the bridge before validation, redaction or delivery, including malformed items and duplicates fetched by separate clients. A poll at its record limit signals possible backlog; it does not measure all Windows work or prove records were lost. These counts reset when the process restarts, not when the session pool is reconfigured.

To estimate rates, take two health readings during the same process and divide counter differences by the elapsed time between their `asked_at` timestamps; this is an approximate observation interval, since each health reading also asks the bridge a question. The reports are separate snapshots, so concurrent activity can briefly appear in one before the other. These numbers describe Sentinel's collection work, not Windows health or the cost of each query. They are included if someone deliberately shares a health reading in a Stack or capture.

## The stack

The stack is the evidence a person or an agent has chosen to hand on. It lives on the server so the desktop, the phone and the agent see one stack.

One index item in `GET /api/stack`, `stack_list` and Stack change answers:

```json
{
  "id": "…",
  "added_at": "2026-09-20T18:10:02.000Z",
  "kind": "reading",
  "title": "Critical and error records, last 50",
  "rank": 3,
  "verbosity": "full",
  "provenance": { "reading": "events", "params": { "log": "System", "count": 50 }, "asked_at": "2026-09-20T18:09:55.000Z", "outcome": "ok", "count": 50 },
  "ids": null,
  "note": null
}
```

| Field | Meaning |
| --- | --- |
| `kind` | `reading` (a whole reading), `selection` (some records chosen by `RecordId` or `Log:RecordId`, or signals chosen by string signal ID, in `ids`), `note` (text the person or agent wrote) |
| `rank` | 1 first to 5 last in the composed handoff; default 3 |
| `verbosity` | `summary` (a compact record table for ordinary logs, with first and last five rows, leading sources and cutoff beyond 100 rows; `events` and `record` also keep collection and retention reach; for `crash`, composed stops with source and retention context; for `faults`, grouped application and live-kernel meaning, selected interpreted entries and source reach; for `changes`, interpreted entries with source outcomes and coverage; for `storms`, coverage, collection, bounded timeline highlights, fixed-header counts, returned signature counts and up to three signature sample references, plus report-traffic status and the not-marked lead only in live windows and an explanation for their absence in historical windows; requested per-report references stay in the stored item and their omissions are counted in the summary; for `whea_reports`, channel coverage, PreviousError totals and bounded report-time highlights; or signal identity, title, summary and source readings) or `full` (the stored sections, or exact selected records beside their interpretation). Defaults to `summary` for whole `crash`, `faults`, `storms` and `whea_reports` readings and for whole `events`, `record` and `whea` readings over 100 rows; selections default to `full`. Either choice can be changed in the Stack. An observation whose requested summary uses full stored sections says so; a compact projection may still carry every interpreted entry up to its reading's limit. |
| `provenance` | The saved reading's name, parameters, response-time `asked_at`, outcome and count, or null for a note. A reading or selection with missing or malformed saved evidence has a provenance object with unknown fields set to null, so it cannot look like a note. This is an index, never a partial evidence envelope: it has no `reading` or sections field. `asked_at` is the reading's response-time stamp, not necessarily when its query began. The full stored item, including its complete reading and method, is at `GET /api/stack/items/{id}` or `stack_item(id)`. |

Index answers are redacted by default, and their `redacted` list describes only fields in the index. A full item's reading can contain further private values; ask for that item to see its own redaction result. The Stack file, composed handoff and captures still keep the complete reading. An agent that takes a reading with `stack_add(take=…)` receives the index; call the reading directly or `stack_item(id)` to inspect its evidence.

| Route | Does |
| --- | --- |
| `GET /api/stack` | `{ "items": [index items], "prompt_id": "...", "system_prompt": true }`; no stored reading is copied into this routine answer |
| `PATCH /api/stack` | Change `prompt_id` or `system_prompt`; returns the same compact index state |
| `POST /api/stack/items` | Add an item; returns its index entry. Body: `kind`, optional `title`, `rank`, `verbosity`, `ids`, `note`, and either `take: { "name": "...", "params": {...} }` (the server takes a new reading now) or `envelope: { ... }` (a reading the caller already holds, stored as given). A selection needs distinct IDs present in that reading: `RecordId` for a record unique within the reading, `Log:RecordId` when records from different logs share a number, or string `id` for a signal. Ambiguous numeric selections are refused; an older saved selection with that ambiguity renders a warning instead of including both logs' records. The composed signal selection keeps the signal section's basis and, at full verbosity, its rule evidence. Re-adding the same observation and selection is refused with `409`, including the existing item ID and observation time; numeric and qualified IDs of one log row are equivalent. A later observation of the same reading is a new item. A `take` always makes a new observation. After an uncertain add, inspect the index. If the item appears there, the add succeeded; do not re-add it. If absent, retry with the original held envelope when possible; retrying a `take` makes a new observation. A redacted saved reading is not a reliable retry key. Supplied envelopes require `asked_at` with `Z` or an explicit UTC offset. |
| `GET /api/stack/items/{id}` | One complete stored item, including its original reading, redacted unless `unredacted=true`; `404` when absent. MCP: `stack_item(id)`, with a reason required for unredacted data. |
| `PATCH /api/stack/items/{id}` | Change `rank`, `verbosity` or `title`; returns the index entry |
| `DELETE /api/stack/items/{id}` | Remove one |
| `DELETE /api/stack` | Clear |
| `GET /api/stack/composed` | `{ "text": "...", "items": 4, "redacted": [...], "prompt": {...}, "stack": {...} }`: the handoff as Markdown, prompt status and same-snapshot compact Stack index. The chosen prompt comes first when included, then the items by rank, each headed with kind, class, provenance, count and warnings and rendered by verbosity; redacted unless `unredacted=true` |
| `GET /api/prompts` | The prompt library: `{ "prompts": [ { "id", "name", "description", "content", "builtin" }, ... ] }`; six presets to start |
| `POST /api/prompts`, `PATCH /api/prompts/{id}`, `DELETE /api/prompts/{id}` | Yours to add, edit and delete, presets included; a deleted preset stays deleted |

A supplied Stack envelope must carry the reading, a timezone-qualified `asked_at`, outcome, params, method and section shapes returned by the API; malformed envelopes are refused before storage. An unreadable or malformed saved Stack or prompt file returns `503` and is never treated as an empty file or overwritten by an edit. Its body keeps `error=saved_context_unavailable`, adds a `reason`, and gives a plain `detail`; MCP refusals lead with the same reason:

| Reason | What is known | Next step |
| --- | --- | --- |
| `busy` | The cross-process lock was not obtained; this request did not read or change the saved file. | Retry once. If it persists with no other operation running, check whether this directory supports file locks. |
| `unreadable` | The directory, lock file or saved file could not be opened or read; this request did not change it. | Check access and retry. |
| `invalid` | Saved bytes could be read but are not valid UTF-8, JSON or the required shape; they were left intact. | Keep a copy and follow the recovery steps below. |
| `not_saved` | Preparing a replacement failed before the saved file was replaced. | The change did not land; retry when the write problem clears. |
| `uncertain` | Replacement or a later operation could not be confirmed. | Read the saved state before retrying an edit. |

A missing Stack file starts empty; a missing prompt file seeds the preset library on first read. A capture's saved Stack and composed handoff use one Stack snapshot; remove, clear and prompt deletion answer with the state their own edit wrote, even if another client edits immediately afterward. Concurrent requests to one server queue for each saved file. If a separate process holds its file lock, the lock attempt can time out after five seconds with `busy`. A hard stop during a write may leave a dot-named `.stack.json.<32 hex>.tmp` or `.prompts.json.<32 hex>.tmp` file beside the saved files. It may hold unredacted evidence or a recoverable partial write. The app preserves it for manual review and never treats it as the saved file. [The synthetic Stack measurement](measurements/stack.md) reproduces direct storage cost without reading installed data. Storm summaries show the five highest-count and five most recent active buckets, with at most three signature counts per highlight, and the top five overall signatures plus up to three recent dominant signatures. They report omitted counts; full verbosity preserves the original arrays and samples. Summary warnings show at most ten entries of 250 characters each and count any further warnings.

Async MCP Stack and prompt operations, capture listing, and HTTP Stack add run their saved-file work in worker threads, so a request waiting for one file's lock does not stop unrelated requests on the event loop. A Stack edit that has begun in a worker finishes and publishes a handoff-change notice even if its caller cancels; a refusal publishes nothing. A cancelled caller may not receive the completed edit's answer, so inspect the Stack before retrying it. Waiting for the saved-file lock can still delay that one request.

An `events` or `record` summary carries `collection` and `coverage` beside a bounded row table. The Record column identifies a log-local `RecordId`; its `Log:RecordId` form can be selected from that held reading when the source log is known. Windows can reuse an ID after clearing a log, so compare the timestamp before treating a later lookup as the same event. A selected row carries source context and its exact stored raw record at full verbosity. Older saved envelopes without collection or coverage explicitly say that their source outcome or retention reach is unknown. Coverage describes the reach of the returned query under its limit; it does not prove Windows emitted every event.

A whole `crash` summary carries up to 20 composed stops in returned order, with their separate stop, restart, announcement and report times, bug-check qualification, dump match, last record before restart, source outcomes and retention reach. It lists decode errors separately and names any omitted stops or errors. A selected crash record carries every composed stop that references it, plus source context and the selected raw rows at full verbosity. A whole `faults` summary carries the returned by-kind counts, up to ten application groups and ten live-kernel groups with omission counts, ten interpreted entries sampled from both ends when there are more, plus Application log query and retention context. A selected fault record includes the decoded entry that refers to it, including another raw row grouped into the same live-kernel report. In summaries, free text inside projected section data is clipped at 250 characters; section bases remain intact. Full verbosity keeps the stored sections and exact selected raw records. These are bounded views of the returned evidence, not a count of all machine faults or a cause diagnosis.

In the current crash reading, `no_bugcheck_recorded: false` can accompany a named bug check, a report-only stop, or an undecodable 41. It does not by itself say why a bug check is absent; read `bugcheck`, the source outcomes and retention together. `null` explicitly means the reading cannot establish absence from an otherwise code-zero 41.

If `stack.json` or `prompts.json` reports `invalid`, stop the app before changing the file in the data directory named in [deployment](DEPLOY.md). Keep a copy of the original bytes; moving the damaged file aside makes the next start create a new empty Stack or seed the prompt library. Review any matching dot-named temporary files before removing them; they are not loaded automatically and may contain private evidence. For `busy` or `unreadable`, check the reported access problem first. For `uncertain`, inspect the saved state before retrying. The app never overwrites a damaged saved file with an empty one or deletes recovery scratch automatically.

`GET /api/stack/composed` returns the handoff Markdown in `text`, the item count, redaction labels, a compact `stack` index, and `prompt: {id, state, reason}`. The index and text come from one saved Stack snapshot. `state` is `included`, `off`, `none`, `missing`, or `unavailable`; `reason` is a stable saved-file reason when the selected prompt library could not be read. A missing selected prompt or unreadable prompt library puts an explicit notice in the Markdown and leaves readable Stack evidence available. A damaged Stack still returns 503. The MCP `compose` tool carries the same object as structured content, while the handoff resource exposes the same Markdown. The composed text is what the dashboard copies to the clipboard or downloads as a Markdown file. An agent reads the same text and needs no clipboard.

## Captures

`POST /api/captures` takes every reading that needs no exact file or event selection, writes a ZIP into the data directory and returns it, with the file's name in the `X-Capture-Name` header. It includes heavy readings, so give it a long timeout. Members: `readings/<name>.json` (one envelope per taken reading), `stack.json`, `composed.md`, and `manifest.json`, which lists exactly the members with each reading's outcome and byte size, the tool's version, the redaction applied and the names of selection-dependent readings omitted. `readings/whea.json` is a bounded preview; the manifest marks its scope, and selected `whea_record` raw fields, full CPER bytes and decoded detail are not in the ZIP. A failed attempted reading stays in the ZIP with its failure outcome; an omitted reading is never presented as a machine failure. If saved Stack data is unavailable, the capture still keeps its machine readings, omits `stack.json` and `composed.md`, and names each in `manifest.unavailable`; the original saved file is left intact. If only the selected prompt is missing or its library cannot be read, `composed.md` still carries the saved Stack evidence and an explicit prompt notice. Its manifest member records `prompt` status and the bounded listing exposes `prompt_state`. The ZIP is redacted unless `unredacted=true`. When an agent takes an unredacted ZIP through `capture_create`, its required reason is also recorded in that ZIP's manifest. A capture receives its public name only after the ZIP and manifest are complete; concurrent captures in the same second keep distinct names. Canceling while readings are taken removes the pending file. Once saved-context assembly begins, its worker finishes one complete listed capture or closes and attempts to remove a failed pending file even if the caller leaves; inspect the capture list before retrying after a timeout. An abrupt process kill can leave a dot-named pending file in the capture directory; one older than 24 hours is retried for removal at the next capture or listing and is never exposed by the capture API. `GET /api/captures` lists each completed file's name, bytes and file modification time (`created_at`), plus a bounded summary of its manifest: `status=read` carries `captured_at`, `unredacted`, the taken reading count, omitted reading count, unavailable saved-context members and counts by outcome; `missing`, `unreadable` or `limit` leave privacy and outcomes unknown. Listing reads only up to 256 KiB of each manifest, not the reading members, and does not validate the whole archive. `GET /api/captures/{name}` returns one. The tool never deletes a completed capture and nothing is sent anywhere.

## What is not here

No live telemetry as a service, no prediction, no full crash-dump analysis, no diagnosis. `dump_header` reads bounded structural metadata; it does not inspect the stack, module contents or memory streams, validate the whole file, or infer a culprit. A burst of corrected errors, a gap in the log or a correlated event is a lead; the reading belongs to whoever holds the evidence.

No temperature, voltage, fan speed or power-draw telemetry either, and that is a decision rather than a gap. What Windows exposes without help is the ACPI thermal zone (`MSAcpi_ThermalZoneTemperature`), which on a desktop board commonly reports a zone that is not the processor, or nothing at all; the sensors a person actually wants sit behind a Super I/O chip or the processor's own management interface, and reaching them means loading a vendor kernel driver — a different trust posture from reading a log Windows already wrote, and one this tool will not take on to report a number. Both of the diagnostic efforts this tool came out of reached for HWiNFO by hand when a temperature mattered, and that stays the answer: run the sensor tool beside this one, and hand its reading to the same conversation.
