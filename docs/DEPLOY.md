# Installing System Sentinel

## By hand: download and double-click

`SystemSentinel.exe` is the whole tool in one file: the server, the dashboard and the decoder. Nothing else needs to be installed.

1. Download it from the latest release, https://github.com/SuperDuperDave/system-sentinel/releases/latest, and leave it wherever your browser put it, as long as that is a local disk (it will not start from a network or `\\wsl.localhost` path). The first time it runs it copies itself into `%LOCALAPPDATA%\SystemSentinel\` and starts that copy, so Downloads is a fine place to run it from; the file you downloaded is then yours to keep or delete.
2. Double-click it. The file is not code-signed, so Windows asks once before running it: either *Windows protected your PC* (click *More info*, then *Run anyway*) or *The publisher could not be verified* (click *Run*). To check what you downloaded first, `Get-FileHash SystemSentinel.exe` in PowerShell prints its SHA-256 and the release page lists the expected value. Which version it is, is in the file: right-click, *Properties*, *Details*.
3. Within a few seconds your browser opens on the dashboard, already signed in, and the mark sits in the system tray: *Open dashboard*, *Sign in another device*, *Copy address for agents*, *Start with Windows*, a submenu named for the version it is running with *Check for updates…* and *Remove from this computer…* in it, and *Quit*. Double-clicking the file again opens the dashboard. It creates its token and keeps its stack, its prompts and its captures under `%LOCALAPPDATA%\SystemSentinel\`.

If the Stack says its saved data is unavailable, the tool leaves the original `stack.json` or `prompts.json` untouched. A temporary file lock may clear on retry. For a damaged file, quit the app, copy the file for recovery, then move it aside; reopening starts a new empty Stack or prompt library. Keep the original copy until you have reviewed it.

To build the file yourself instead: `build\windows\build.ps1` from the repository on Windows (Python 3.11 or newer and Node 22 or newer; about five minutes the first time).

## With your agent

Copy one of the two blocks below and paste it to the agent running on the Windows machine you want to read (Claude Code, Codex or any agent with a shell). Both end with the tool running, proven, and registered as an MCP server, so the agent reads the machine through the tool instead of writing its own scripts; both are safe to run twice, because every step checks before it acts.

**The short prompt** installs the published release and updates it: one file, nothing to build, no Git, Python or Node, done in a minute. It is one prompt for both, because installing and updating are the same act — the file it downloads puts itself in place either way — and it stops early when the machine already runs what is published. **The long prompt** installs from source, for a machine where you want the code on disk and the `system-sentinel` command line; it needs Git, Python 3.11 or newer and Node.js 22 or newer, and installs them with winget if they are missing.

Neither sends machine readings or the token to GitHub or a hosted service, opens a port beyond localhost, or installs a service. Running at logon and reaching the machine from a phone are the optional steps at the end; an authenticated phone reading travels over the private transport you configure.

### The short prompt

```text
Install System Sentinel on this Windows machine from its published release, or update the copy that is already there, and prove it works. This prompt is the tool's own installation note (docs/DEPLOY.md in https://github.com/SuperDuperDave/system-sentinel); I chose to install it and I own the decision. Work in PowerShell. Do each step, check its result, and stop and tell me if a check fails. Do not skip a check because the step looked successful.

0. Look before you run. Read README.md and docs/API.md at https://github.com/SuperDuperDave/system-sentinel and tell me in two sentences what the tool does and what it listens on (it binds to localhost; its updater contacts GitHub only when asked, and sends no machine readings or token). The file you are about to download is built from that repository by build\windows\build.ps1 and the release lists its SHA-256. If what you read contradicts that, stop and show me.

1. Download it to a temporary path. Run `$new = "$env:TEMP\SystemSentinel.exe"` and `Invoke-WebRequest -Uri https://github.com/SuperDuperDave/system-sentinel/releases/latest/download/SystemSentinel.exe -OutFile $new`. Temporary on purpose: the file installs itself, and where it ends up is its business, not yours.

2. Check it. Run `(Invoke-WebRequest -UseBasicParsing https://github.com/SuperDuperDave/system-sentinel/releases/latest/download/SHA256SUMS.txt).Content` and `(Get-FileHash $new).Hash`. The hash must be the one on the SystemSentinel.exe line of that list. If it is not, delete the file and stop.

3. Is this already what is installed? The installed copy is "$env:LOCALAPPDATA\SystemSentinel\SystemSentinel.exe". If it exists, run `(Get-FileHash "$env:LOCALAPPDATA\SystemSentinel\SystemSentinel.exe").Hash` and compare it with the hash from step 2. If they are equal and `Get-Process SystemSentinel -ErrorAction SilentlyContinue` names a running process, this machine already runs this build: run `Remove-Item $new` and skip to step 5. Otherwise continue — a different hash is the update.

4. Unblock it and start it. Run `Unblock-File $new`: Windows marks a downloaded file and will not start it unattended until someone answers a dialog, and this is you deciding to run the file you just checked. Then run `Start-Process $new`. It copies itself into "$env:LOCALAPPDATA\SystemSentinel\" and starts the installed copy, which serves on http://127.0.0.1:8000, opens the dashboard in the browser already signed in and sits in the system tray; if an older copy is already serving, it asks that one to quit first and takes its place. One exception: a running 1.0.0 predates the quit route and cannot be asked, so the new file says so in a message box and changes nothing; if `(Invoke-RestMethod -Uri http://127.0.0.1:8000/api/readings -Headers @{ Authorization = "Bearer TOKEN" }).version` prints 1.0.0, run `Stop-Process -Name SystemSentinel` (1.0.0 has no gentler way) and `Start-Process $new` again. Wait fifteen seconds, then run `Remove-Item $new`: the installed copy is the one that matters now.

5. The token. Run `Get-Content "$env:LOCALAPPDATA\SystemSentinel\token"` and keep the value; call it TOKEN. Never paste it anywhere except the two places below.

6. Prove it. Run `Invoke-RestMethod -Uri http://127.0.0.1:8000/api/readings -Headers @{ Authorization = "Bearer TOKEN" }`. Confirm two things: its "readings" include "health", "events" and "record", and its "version" is what `(Get-Item "$env:LOCALAPPDATA\SystemSentinel\SystemSentinel.exe").VersionInfo.ProductVersion` prints. The file and the server agreeing is how you know the process answering is the copy you just installed, and not an older one still holding the port. Then confirm that the same address without the header answers 401: `try { Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8000/api/readings } catch { $_.Exception.Response.StatusCode.value__ }` prints 401 (Windows PowerShell 5.1 throws on a 4xx; that is expected).

7. Register the MCP server so agents on this machine can use it. This is a durable change to your own configuration on this machine and I want it: it lets you read this machine through the tool in future sessions instead of writing scripts. First run `claude mcp list`. If it already names system-sentinel, leave it alone and say so — an update does not change the token, and `claude mcp add` with a name that exists does not replace it, it exits 1 with "already exists in local config". Only if the token changed (which happens only if the data directory was deleted) run `claude mcp remove system-sentinel` first. Otherwise, if Claude Code is installed, run `claude mcp add --transport http system-sentinel http://127.0.0.1:8000/mcp --header "Authorization: Bearer TOKEN"`. For any other MCP client, the address is http://127.0.0.1:8000/mcp with that Authorization header. Every tool it offers is one of the readings you saw in step 6; `claude mcp remove system-sentinel` undoes this.

8. Tell me: which version is running and whether this was an install or an update; the dashboard is at http://127.0.0.1:8000/ and is already open; the mark in the tray has Start with Windows, Sign in another device for my phone, and a submenu named for the version with Check for updates and Remove from this computer in it; the API reference is at http://127.0.0.1:8000/api/docs. Then read the machine through it once: take the "events" reading with count 5 (GET http://127.0.0.1:8000/api/readings/events?count=5 with the header, or the events tool) and tell me the outcome and how many records came back.
```

### The long prompt

```text
Install System Sentinel on this Windows machine from source and prove it works. This prompt is the tool's own installation note (docs/DEPLOY.md in its repository); I chose to install it and I own the decision. Work in PowerShell. Do each step, check its result, and stop and tell me if a check fails. Do not skip a check because the step looked successful.

0. Look before you run. After step 2 clones the repository and before anything is installed, read README.md, pyproject.toml, sentinel/app.py, sentinel/auth.py, sentinel/update.py and sentinel/mcp_server.py, and tell me in three sentences: what the server does, what it listens on, and whether anything it does sends data off this machine (the server binds to localhost; the updater contacts GitHub only when asked and sends no machine readings or token; handoffs go to the clipboard and captures stay on disk). If what you read contradicts that, stop and show me.

1. Prerequisites. Run `git --version`, `python --version` and `node --version`. One that prints "is not recognized" is missing; so is python when it prints "Python was not found; run without arguments to install from the Microsoft Store" (that is the Store's placeholder, not an installation). Install what is missing with winget, in exactly this form so that it runs without a prompt: `winget install --id Git.Git --exact --source winget --accept-source-agreements --accept-package-agreements`, then the same with `--id OpenJS.NodeJS.LTS`, and last with `--id Python.Python.3.13`. If winget itself is not recognized, stop and tell me: I will install App Installer from the Microsoft Store (or Git, Node and Python from git-scm.com, nodejs.org and python.org) and you can continue. After installing, make this session see the new PATH: `$env:Path = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + [Environment]::GetEnvironmentVariable('Path','User')`. Run the three version commands again (Python 3.11 or newer, Node 22 or newer) and tell me what you installed. If python still prints the Store's placeholder, the Store's alias is shadowing the interpreter you installed: use `py -3.13` in place of `python` in step 3.

2. Source. If a folder named system-sentinel exists in the current directory, `cd system-sentinel` and run `git pull`. Otherwise run `git clone https://github.com/SuperDuperDave/system-sentinel.git` and `cd system-sentinel`.

3. Python package. If `.venv` does not exist, run `python -m venv .venv` (or `py -3.13 -m venv .venv`, see step 1). Then run `.venv\Scripts\python -m pip install -e .` and confirm it ends without an error.

4. Dashboard. Run `cd dashboard`, `npm ci`, `npm run build`, `cd ..`. A warning from npm that a package has install scripts "not yet covered by allowScripts" is a notice, not a failure: continue. If `npm ci` fails fetching a platform-specific optional package (a user-level `.npmrc` that pins `os=linux` does this), run `npm ci --os=win32 --cpu=x64` instead and tell me. Confirm that `sentinel\static\index.html` now exists.

5. The bridge. Run `.venv\Scripts\system-sentinel check`. It prints a JSON reading; confirm its "outcome" is "ok" and it reports a PowerShell version. If the outcome is anything else, stop and show me the reading.

6. The token. Run `.venv\Scripts\system-sentinel token` and keep the value; call it TOKEN. Never paste it anywhere except the two places below.

7. Serve. First see whether something is already serving that port: `try { (Invoke-RestMethod -Uri http://127.0.0.1:8000/api/readings -Headers @{ Authorization = "Bearer TOKEN" }).version } catch { "nothing" }`. If it prints a version, a System Sentinel holding this machine's token is already answering — the release's executable, or a server from an earlier run. Leave it and skip to step 8 if all I wanted was the tool running; stop it first if this checkout should be the one serving: `Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/quit -Headers @{ Authorization = "Bearer TOKEN" }` answers quitting and the process exits within a few seconds. Tell me which you did. Then start the server in the background with `Start-Process -FilePath ".venv\Scripts\system-sentinel.exe" -ArgumentList "serve" -WindowStyle Hidden`, wait five seconds, then run `Invoke-RestMethod -Uri http://127.0.0.1:8000/api/readings -Headers @{ Authorization = "Bearer TOKEN" }` and confirm it lists readings including "health", "events" and "record". Then confirm that the same address without the header answers 401: `try { Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8000/api/readings } catch { $_.Exception.Response.StatusCode.value__ }` prints 401 (Windows PowerShell 5.1 throws on a 4xx; that is expected).

8. Register the MCP server so agents on this machine can use it. This is a durable change to your own configuration on this machine and I want it: it lets you read this machine through the tool in future sessions instead of writing scripts. If Claude Code is installed, run `claude mcp add --transport http system-sentinel http://127.0.0.1:8000/mcp --header "Authorization: Bearer TOKEN"`. For any other MCP client, the address is http://127.0.0.1:8000/mcp with that Authorization header. Every tool it offers is one of the readings you saw in step 7; `claude mcp remove system-sentinel` undoes this.

9. Tell me: the dashboard is at http://127.0.0.1:8000/ (enter the token once; it is kept in the data folder shown by `.venv\Scripts\system-sentinel where`), the API reference is at http://127.0.0.1:8000/api/docs, and the agent guide is docs/API.md in the repository. Then read the machine through it once: take the "events" reading with count 5 and tell me the outcome and how many records came back.
```

## Optional: run at logon

With the release, *Start with Windows* in the tray's menu does it (a shortcut in your Startup folder; the same entry removes it). From source, paste after the long prompt:

```text
Create a scheduled task that starts the server at logon: `schtasks /Create /F /TN "System Sentinel" /SC ONLOGON /RL LIMITED /TR "\"$PWD\.venv\Scripts\pythonw.exe\" -m sentinel serve"` from the repository folder, then confirm with `schtasks /Query /TN "System Sentinel"`.
```

## Optional: reach it from your phone

The server listens on localhost and every API request needs the token; reaching it from elsewhere is a transport in front of that boundary, chosen by you.

- **Tailscale (recommended).** Private by construction: only devices on your own tailnet can reach the machine, and every request still needs the token. Needs a Tailscale account (free for personal use) and the Tailscale app on the phone, signed in to the same account. Paste: `Install Tailscale with winget (`winget install --id Tailscale.Tailscale --exact --source winget --accept-source-agreements --accept-package-agreements`), sign in with `tailscale up`, then run `tailscale serve --bg 8000` and tell me the https address it prints. If it says HTTPS is not enabled for the tailnet, it prints a link where I enable it once; tell me the link and wait (leave Funnel off: the dashboard stays private to my own devices).` Once `tailscale serve` is running, *Sign in another device* in the dashboard or the tray shows that address as a link and a QR code: scan it on the phone and it lands on the dashboard signed in, without anyone reading the token.
- **A Cloudflare quick tunnel.** No account, but the address is public to anyone who has it and changes every time the tunnel restarts; the token is the only boundary. Suitable for a short session, not for a machine left on. Paste: `Install cloudflared with winget (`winget install --id Cloudflare.cloudflared --exact --source winget --accept-source-agreements --accept-package-agreements`), run `cloudflared tunnel --url http://127.0.0.1:8000`, and tell me the trycloudflare.com address it prints.`

## Updating it

A newer file replaces the installed copy and nothing else. The token, the stack, the prompts and the captures belong to the data directory and are left where they are, so an update does not sign anyone out or lose a handoff, and an agent registered against the tool stays registered.

**A person, from 1.1.0.** Choose *Check for updates…* in the tray's version submenu. The tool asks GitHub for the latest published stable release at that moment; it does not check on a timer. If a newer version is available, it asks before downloading the executable and checksum list. It checks GitHub's SHA-256 asset digest, the release's checksum list, the downloaded bytes and the executable's Windows version before starting the new file. That file asks the running copy to quit, replaces it and reopens the dashboard. The updater sends no token or machine readings to GitHub. If the check or download fails, the installed file stays in place and the release page is offered as a fallback. A 1.0.1 installation has the older tray action, which opens the releases page; install 1.1.0 manually once to gain this flow. For the much older 1.0.0, first *Quit* it from the tray before starting the newer file, because 1.0.0 cannot answer the quit request.

**An agent.** Paste the short prompt again. It compares the published SHA-256 with the installed copy's, stops at that comparison when they are the same file and it is already running, and otherwise downloads, checks, installs and proves the result by the version the server reports.

**From source or a terminal.** `system-sentinel update` checks the latest stable release and prints its version without installing. On Windows, `system-sentinel update --install` downloads, verifies and starts a newer release through the same handoff. A source checkout remains available for development; the command does not replace the checkout.

Going back is by tag: every release stays downloadable from its own page, https://github.com/SuperDuperDave/system-sentinel/releases/tag/v1.0.0 and so on for each. An older file will not overwrite a newer installed copy: it starts the newer one instead, and tells you so if that one is already running. So going back means removing the installed program first: *Quit* in the tray, delete `%LOCALAPPDATA%\SystemSentinel\SystemSentinel.exe` (that one file; the rest of the folder is your data), then double-click the older download.

## Which version you have

Four places, and they should agree:

- **The file.** Right-click it, *Properties*, *Details*. In PowerShell: `(Get-Item "$env:LOCALAPPDATA\SystemSentinel\SystemSentinel.exe").VersionInfo.ProductVersion`.
- **The tray.** The submenu above *Quit* is named for the version that is running.
- **The dashboard.** The Agents view carries it, with a link to the releases page.
- **The API.** `version` on `GET /api/readings`, beside the catalog: what the process answering right now is.

The file and the API disagree only while an older copy is still serving the port and a newer one has been put in place but has not started. Starting the installed copy settles it.

## Removing it

*Remove from this computer…* in the tray's version submenu. It names what goes and what stays, asks once, turns *Start with Windows* off, quits, and deletes its home once the process has exited.

By hand, the same four steps:

1. Turn *Start with Windows* off in the tray, or delete the *System Sentinel* shortcut from the folder `shell:startup` opens.
2. *Quit* in the tray, or `Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/quit -Headers @{ Authorization = "Bearer TOKEN" }`.
3. `Remove-Item -Recurse -Force "$env:LOCALAPPDATA\SystemSentinel"`. That is the program, the token, the stack, the prompts and the captures, and it cannot be undone.
4. `claude mcp remove system-sentinel`, once for each agent registered against it.

What stays is yours: the file you downloaded, wherever you put it, and anything you took out of the tool yourself — a handoff you pasted somewhere, a capture you copied out of the data directory. The tool wrote nowhere else. No service, no registry keys, nothing outside its home but the Startup shortcut that step 1 removes.

## If something goes wrong

| What you see | What to do |
| --- | --- |
| *Windows protected your PC*, or *Open File - Security Warning: The publisher could not be verified* | Expected: the file is not code-signed. Check its SHA-256 against the release's list, then *More info* → *Run anyway*, or *Run*. `Unblock-File` takes the mark off for good, which is what the short prompt does once the hash has checked out. |
| Nothing happens after the double-click, and a message box names the port | Something else holds that port. If it is System Sentinel, it is already running — use *Open dashboard* in the tray. If a copy is still stopping, wait a few seconds and start it again. `Get-NetTCPConnection -LocalPort 8000 -State Listen \| Select-Object OwningProcess` names the process. The message box says where `launcher.log` is; the log keeps two backups behind it. |
| The mark is in the tray but no browser opened | This machine has no browser registered for `http`, or the one it has did not answer; the message box says which. Open http://127.0.0.1:8000/ yourself, or reach it from a phone with *Sign in another device*. |
| The dashboard asks for an access token | This browser holds no session: it is one the tool did not open — another profile, or a device that followed no link. *Open dashboard* in the tray signs a browser in without the token; for a phone, *Sign in another device*. |
| Defender, or another scanner, quarantines the file or holds it for a while | A single-file executable with no signature is unfamiliar to a scanner. Check the bytes three ways: the SHA-256 against the release's list, the digest GitHub computed for the asset (`gh release view <the tag you downloaded> --json assets --jq '.assets[].digest'`), and, from 1.0.1, the build provenance attestation: `gh attestation verify SystemSentinel.exe -R SuperDuperDave/system-sentinel`. Whether to make an exclusion is your decision. |
| `claude mcp add` exits 1 with *already exists in local config* | It is registered already, and `add` does not replace a registration. Leave it; an update does not change the token. If the token did change, `claude mcp remove system-sentinel` and add it again. |
| `Get-FileHash` does not match the published list | Do not run the file. Delete it, download it again, and if it still differs, stop and say so. |
