# Space Atlas — working design

Status: the [interactive concept](space-atlas-prototype/index.html) uses invented data. The dashboard now has an on-demand Windows-backed Space view with tiles, a planet and a shared walk path. Neither surface performs cleanup.

## The job

A person wants to answer three questions: **where is the space**, **what changed**, and **what could be investigated safely**. An agent needs the same observations with source, coverage and stable references. A large rectangle alone answers only the first question. This feature belongs in System Sentinel because unexplained disk pressure is a machine condition, and a selected folder can travel into an investigation handoff without the tool deciding what to delete.

## The surface

The top strip reconciles filesystem-reported used and free capacity with space attributed by a scan. The difference is labeled as a **gap to volume used**, never presented as a folder or as reclaimable. The main region pairs a spatial surface with a ranked trail. The surface gives quick orientation and a memorable location; the trail keeps labels, exact numbers and keyboard/phone navigation legible. Both represent the same current directory and the same selection. A click inspects in place. An explicit zoom action enters a folder. Breadcrumbs, Back and a focus-preserving return recover position.

David clarified that this is a **visual navigator**, not a static map. Tile, planet, and storage archaeology views must all descend through the same measured hierarchy. The current scope, selected node, parent chain, scan identity, measurement basis, and coverage are shared state; switching visualization must not reset any of them. Each view offers inspect, enter, ascend and jump-to-ancestor controls. A file is a leaf with inspection and evidence actions, not a fake new world. Disk and volume capacity are context above the scanned home scope until a volume-wide scan exists; their unattributed remainder must never become a navigable folder or a region with invented children.

The second concept makes the surface a **file planet**. Groups occupy continuous regions of one rotatable sphere. Each region's spherical surface area is proportional to its allocation within the displayed scope; small, sparse points are texture and do not stand for files. The prototype initially used only equal sized dots, which concealed the size comparison. David's critique prompted the continuous territories, labels with GiB and percentage, and a full surface strip with a ranked key. Only the near hemisphere is visible, so its projected patch is *never* a percentage chart; the full surface strip and trail carry exact comparison. Drag rotates, scroll or pinch toward the selected region dives into its children, and scrolling out or using the breadcrumb returns to the parent. The original flat map remains an alternate view when a spatial overview is more useful. In production, a selected group must retain an opaque identity and camera orientation across the transition so the dive does not lose the person's place. The prototype's globe is a visual interaction study using invented data, not a representation of real file counts or bytes.

In the live dashboard, area encodes measured allocation and hatching marks a partial lower bound. Hue identifies a territory; it does not classify safety. The inspector compares logical length with allocation and draws a byte-weighted last-write core sample. Selecting inspects, and entering asks for a fresh child walk. The concept's Growth mode uses invented comparable deltas; live growth needs retained comparable scans. A small region never implies a safe deletion. The concept uses invented values to test the interaction grammar; its values are not measurements.

## Measurement contract before real data

- Run disk observations through the existing Windows bridge. Start with fixed volumes and a chosen subtree. Snapshot time, root identity and collection outcome must be explicit. Scan on demand; never start a whole-disk walk in the background by opening the dashboard.
- Volume used and free come from the filesystem. File logical length and allocated bytes are distinct. Compressed/sparse files and cloud placeholders may have a large length and small local allocation. Avoid file-content reads and placeholder hydration.
- On Windows, the [extended directory information record](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_extd_dir_info) can report allocation, length, reparse tag and file ID in one enumeration. Test its availability and field behavior on the host before choosing it over per-file metadata calls; do not label logical length as allocation when the native query fails.
- Never traverse a junction, symlink, mount point or other reparse directory. Record its presence and reason. Identify hardlinks by volume plus file identity and count their allocation once *within the observed scope*. This does not establish that removing one path would free those bytes; other links may exist outside it.
- Each subtree carries coverage: complete, access denied, skipped link, timeout, or other error, with counts and bounded examples. A partial aggregate is a **lower bound**. A failed root is not an empty root. A scan that cannot reconcile with volume used has an explicit unattributed remainder; no guessed allocation fills it.
- Compare scans only for the same volume/root and measurement method. A moved, omitted or unreadable subtree is incomparable, not growth or shrinkage. Save a small numeric/opaque snapshot locally only after an explicit scan; paths and names require an explicit local display or unredacted request. Standard capture, Stack and MCP redaction remain in force.
- A review basket contains references and current observations, not a claim of savings. Recheck paths, hardlinks, source control and application ownership at action time. No delete or trash action belongs in the first release.

## First real slice and acceptance

1. A bounded scan of the current user's Windows home folder with allocated/logical totals, coverage, byte-weighted last-write bands, and top-level directory attribution. The `space` reading is wired to the API, MCP and dashboard and has passed a synthetic Windows host fixture for compressed files, hardlinks, junctions, denial, entry limits, encoded child paths and selected-root reparse refusal. It also returns up to 20 largest observed files as metadata-only leads. An opaque, short-lived `scope_id` on a visible directory row permits a fresh child walk. These independent rescans can re-attribute hardlinks and do not form a reconciled snapshot tree. A browser fixture verified tile and planet switching, desktop and phone layout, selection and descent.
2. A volume ledger that makes attributed, unattributed, used and free add up without pretending the scan sees protected, shared or reserved storage. An opaque node reference supports an on-demand drill-down, so default agent responses and URLs do not carry local paths.
3. Verify a normal scan, an unreadable child, a link, a hardlink, a placeholder, and a scan that stops early on Windows. Check the dashboard on desktop and phone, by keyboard and with reduced motion. Inspect the actual API envelope and MCP response, including default redaction.

Host timing observation on 2026-09-25: a read-only Home walk with names off, `seconds=5` and `max_entries=100000` stopped at the entry cap in about 3.75 seconds, returned 36 top-level rows and 20 largest-file metadata rows, and reported 34 directories unvisited. This is one machine-specific trial, not a guaranteed rate. It confirms that a 30-second default can be partial on a large home tree and that coverage must remain prominent. The synthetic fixture separately verifies correctness cases; a cloud placeholder's hydration behavior and a complete large home walk remain untested.

An end-to-end local drill trial used two shorter named-off scans: Home returned 36 rows before its 20,000-entry cap; selecting one issued opaque directory handle returned a child reading at depth 1 with five rows and the independent-scan warning. The child envelope carried no folder names. This proves the navigation path can work locally; it does not make parent and child one comparable snapshot.

The approved [experience direction](SPACE-ATLAS-EXPERIENCE-2026-09-25.md) includes thirteen further visual and investigative ideas. Their data dependencies include retained hierarchy snapshots with pagination, comparable history, verified change events, target-drive facts and separately chosen content hashing. Review state and possible savings remain separate from measured occupancy. An unreadable area without a reliable bound cannot be assigned a fictional tile area. The recursive planet can request measured child scopes today, but the current API cannot guarantee one coherent snapshot across levels.

## Reference and consultation

[disktree](https://github.com/tobi/disktree) already provides a treemap, smooth zoom, size/files/age modes, name filtering, reclaimable hints, mark/review, disk free space, and careful removal guards. The differentiation here is reconciliation, change, coverage, and a shared human/agent evidence model. A high-effort Claude Opus 5.5 consultation on 2026-09-25 argued for a volume ledger, readable drill-down and scan-to-scan growth. Buddy's scoped critique supported a survey metaphor, persistent scan time, visual certainty, a review queue and a bounded agent handoff. Its planet critique emphasized a full surface key, persistent path, keyboard parity and a graceful flat fallback; its claim that a near-side projected patch preserves spherical area is false because foreshortening depends on orientation. Its earlier suggestion that reclaimable hints and marked review differentiate this design from disktree was incorrect against the reference's README. Both consultations are design input, not implementation evidence.
