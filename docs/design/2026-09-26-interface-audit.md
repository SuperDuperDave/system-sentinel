# Interface audit and three directions, 2026-09-26

Status: phase 1 of the interface overhaul. The audit and the three direction theses below are for David's choice; nothing here changes the application. Read at public commit `7255ed5` (v1.10.1).

Every screen in this note was rendered by the real dashboard over the synthetic fixture server (`docs/screens/fixtures/fixture-server.py`), so nothing from a real machine appears. The captures are in [`audit-2026-09-26/`](audit-2026-09-26/): `<shot>-1440.png` is the first screen at 1440x900, `<shot>-390.png` the first screen at 390x844, and `-full` the whole page where length is part of the finding. [How to take them again](#the-harness) is at the end.

## The five questions

A first-time person opening a machine monitor wants five answers before anything else. The dashboard was measured against each on every view.

| Question | Where the dashboard answers it today | What a first-time person sees |
| --- | --- | --- |
| **Where am I?** | The rail names ten views in three groups: *Evidence* (Record, Hardware errors, Crashes, Machine, Performance, Space), *Interpret* (Diagnostics, Signals), *Carry* (Stack, Agents). | The app opens on **Record**, a System-log browser ([record-1440](audit-2026-09-26/record-1440.png)). The group words describe the tool's method, not the person's situation. Machine adds a row of ten in-page jump links that runs off the phone screen ([machine-390](audit-2026-09-26/machine-390.png)). |
| **Is the machine healthy?** | Nowhere. The one persistent status, *live bridge · PowerShell 5.1 · 4 ms*, is the tool's own connection. | The nearest answers are scattered across four views: a stop list in Crashes, a burst status in Hardware errors, lead counts in Signals ("Counts show patterns, not health or severity"), a load bar in Machine. None is on the first screen. |
| **What changed?** | Each reading says when it was taken. The `changes` reading exists but opens only inside one expanded stop ([crashes-open-1440](audit-2026-09-26/crashes-open-1440.png), *Read change history*). | No view compares now with before. The one surface that shows time across sources, *Windows' reliability record* (a day strip inside Crashes), sits in the middle of a view about stops. Five views carry five window vocabularies: last 50/200/500, 24 hours/7 days/since boot, last 5/20, last 30/100, 1/6/24/48 h. |
| **What should I do?** | Every section ends in the same tool verbs: *Take again*, *Method*, *Stack this reading*, *Add to stack*, *Basis*. | The verbs operate the instrument; none points at the next step in an investigation. Signals' *Inspect leads*, the one forward verb, lives in a view a person must first know to open. Stack's prompt library leads with *Quantum Diagnostician*, *Preventative Oracle* ("Finds problems before they become crashes") and *RMA Prosecutor* ([stack-1440](audit-2026-09-26/stack-1440.png)), names that contradict the product's own promise of no prediction and no diagnosis. |
| **What does my agent see?** | Agents is a setup page: token location, four registration commands ([agents-1440](audit-2026-09-26/agents-1440.png)). | Nothing shows what an agent has read, asked or been handed, and no screen says "an agent reading this would get the same envelope". The parity is true in the architecture and invisible in the interface. |

## View by view

- **Record** ([1440](audit-2026-09-26/record-1440.png), [390](audit-2026-09-26/record-390.png), [open](audit-2026-09-26/record-open-1440.png)). The strongest summary in the app: *Where these entries fall* with a histogram and a top-sources list. Three segmented controls compete with the title at equal weight. Opened rows show the provider, ID, level, record and time in a clean readout; the *records before* list then runs 15:55 into 10:19 with no day marker between them, so the order reads as wrong. Levels are small monochrome glyphs in one colour: a triangle for Critical, a filled disc for Error, a ring for Warning and a smaller filled disc for Information, so Error and Information differ only by the size of a dot a few pixels across.
- **Hardware errors** ([1440](audit-2026-09-26/errors-1440.png), [full](audit-2026-09-26/errors-1440-full.png), [390 full](audit-2026-09-26/errors-390-full.png)). The first screen is four paragraphs of derivation in monospace, including field names (`recent_composition`, `not_marked_burst`). The one fact that matters, a burst of six in one minute with severity *warning*, sits in the second line of that block. The trace that shows it is below the fold and the burst is a squiggle a few pixels wide at the right edge. The page is over 4,000 px on the desktop and more than 6,000 on the phone.
- **Crashes** ([1440](audit-2026-09-26/crashes-1440.png), [full](audit-2026-09-26/crashes-1440-full.png), [open](audit-2026-09-26/crashes-open-1440.png)). The stop row is well designed: bug check, downtime, dump, and three evidence times (last record before restart, Windows' stop estimate, next start). Above it sit *Stops · DERIVED · computed from raw · newest first · Basis* before the first stop. The expanded stop is a long key/value readout; the questions a person has (what happened just before, what changed) are two further disclosures down.
- **Machine** ([1440](audit-2026-09-26/machine-1440.png), [full](audit-2026-09-26/machine-1440-full.png)). The *Machine map* is the closest thing to a home: four parts, a snapshot of load and memory. It is fourth in the rail. When a reading fails, *Not observed* takes the display face and size that a processor name takes, so an unanswered question looks like an answer.
- **Performance** ([1440](audit-2026-09-26/performance-1440.png)). *Who is using the machine?* is the right question, stated plainly. The collection controls (pause, interval) sit in the main reading path on every visit.
- **Space** ([1440](audit-2026-09-26/space-1440.png)) is an empty page with one button until a walk is asked for. The Space Atlas lab it links to ([lab-1440](audit-2026-09-26/space-lab-1440.png)) is the most legible surface the product has: a volume ledger that reconciles, a ranked exact list, an inspector for the selection and an evidence gate that says what the reading supports. It overflows horizontally at both widths (the page is about 1,600 px wide in a 1,440 or 390 px window).
- **Diagnostics** ([1440](audit-2026-09-26/diagnostics-1440.png), [memory](audit-2026-09-26/diagnostics-memory-1440.png)). Four readings behind *Take the reading*. The distinction between readings taken on request and readings taken on arrival is real, and this is the only view that makes it the page's structure.
- **Signals** ([1440](audit-2026-09-26/signals-1440.png)). Good bones: a pattern map by class, inputs with their answered or failed state, leads each with the rule and evidence. The class names (*suppressions, gaps, pressure, transitions, mismatches*) are the detector's taxonomy, not a person's question.
- **Stack** and **Agents**: see the table above. Stack's composed handoff, the thing an agent actually receives, is below a long prompt library.
- **Phone** ([nav-open-390](audit-2026-09-26/nav-open-390.png)). The *Current view / All views* disclosure is sound. Every view keeps the desktop's order, so the phone's first screen is usually the tool's metadata row and a paragraph of explanation.

**What these captures cannot judge.** The fixture answers Windows' reliability record, `changes`, PCIe, constraints, performance history and Space empty or failed, so those surfaces were judged on their empty or failed states only. The reliability day strip inside Crashes exists and was not seen with data.

What works and must survive any direction: the reading envelope's honesty (observed, empty, failed, denied, timeout, unavailable kept apart); exact rows one tap from every summary; *The record before this*; the address carrying the view and moment; held readings that stay visible when a retake fails; keyboard focus management on navigation.

## Structural causes

The symptoms above come from six causes. Fixing a symptom view by view would leave each cause in place.

1. **The navigation mirrors the reading catalog.** Views are, almost one to one, the readings the API offers (`events`, `whea`, `crash`, `hardware`, `performance_history`, `space`, `signals`). That is right for an agent, which calls readings by name, and wrong for a person, who arrives with a situation: *it froze*, *it is slow*, *something is filling the disk*, *I want help*. The groups *Evidence / Interpret / Carry* name the method's stages.
2. **There is no home and no spine.** The default view is a log browser. Time is the product's real unit (a stop, a burst, a lead and *the record before this* all pivot on a moment, and the address already carries one), yet time is not a navigation axis: each view owns a private window and its own vocabulary for it.
3. **Every level of disclosure sits at the first level.** The identity note sets the reading order as *question or state, bounded visual summary, exact evidence, method and raw readout*. The views run it backwards: method metadata (count, taken, ms, Take again, Method, Stack), then class labels (DERIVED, INFERRED, Basis), then the explanation of the rule, then the summary. Evidence classes are the product's integrity, but printed as uppercase badges on every section they become noise; the product needs one quiet, consistent encoding instead.
4. **One voice for everything.** Headings, labels, readouts, buttons and some paragraphs are all monospace; controls are underlined mono text of the same size as the readouts beside them, so a button does not look like a button. The display face at 300 weight in mono makes every title the same shape.
5. **No semantic channel.** The token set has a field, lit and deep grounds, a raised surface and an inspection well, ink, body, muted, rules and one light (phosphor), reserved for *live* and focus. There is no token for attention, stop, unknown or failed, so a critical record, a failed collection and an ordinary row share one colour and differ only by a small glyph or a word. Surfaces differ from the field by a few percent of luminance and are separated by hairline borders (134 `border` declarations that draw a line, of 146 across `dashboard/src/**/*.css` at `7255ed5`, counted with `grep -E 'border(-(top|bottom|left|right))?\s*:'` excluding `none` and `0`), boxes inside boxes on Machine and Crashes. That is the flatness David named: without salience the eye has no entry point.
6. **The agent is an architecture, not a presence.** One API boundary serves the person and the agent, but the interface shows only the person's side. The stack is global, unnamed and unowned, so it cannot be *this investigation*, and nothing records what an agent read: the only log is the server's console access log. The prompt presets with predictive names are server data, so an agent receives them too through `prompts_list`; that is an API defect as well as a screen one.

## Frontier

What leads today in the adjacent fields, and the part that fits Sentinel's jobs. These are interaction models, not looks to copy.

- **Clinical monitors** (bedside and central-station monitors, anaesthesia displays). The unit on screen is the vital sign: a large number, its trend, its source and its limits, with alarms ranked in three priorities that colour, flashing and sound each carry (the IEC 60601-1-8 alarm standard), and a message on screen naming the condition. Review is by *episode*: an event with the waveform before and after it. Research on configural and ecological displays for anaesthesia showed that shapes built from several variables let clinicians see a deviation before reading any number. *Fits:* a stop is already an episode with a before window; redundant encoding is exactly what the level glyphs lack. *Does not fit:* normal ranges. Sentinel cannot say what a normal count of corrected hardware errors is on a given machine.
- **System monitors** (Windows Task Manager and Reliability Monitor, macOS Activity Monitor, btop). Reliability Monitor's one strip of days, each day marked by the kinds of event it holds, is still the clearest answer on Windows to *when did this start*. Task Manager leads with small multiples of live resources. *Fits:* a day strip across sources is a home that answers *what changed* without a verdict.
- **Observability consoles** (Grafana, Honeycomb, Datadog, Sentry). The shared time range: one range drives every panel, and selecting a region of one chart filters the others. Honeycomb's BubbleUp compares a selected region with its baseline and ranks what differs. Sentry makes the *issue* the unit: grouped occurrences with first seen, last seen, count and the events behind them. Notebooks keep an investigation's queries and notes as one document. *Fits:* one time range; the lead or stop as a first-class object with first and last seen; the investigation as a document.
- **Developer tools** (the Chrome DevTools Performance panel, time-travel debuggers). Many tracks on one time axis, a selection that updates a summary without moving the view, and exact entries one level down. *Fits:* it is *inspect without navigating*, the doctrine's second rule, solved for dense time-series.
- **Interfaces shared by a person and an agent.** The field is converging on one state that both read, with the interface as one client of it: MCP resources and tools beside a UI, tools that return renderable UI, agent transcripts that cite what they read, and review surfaces where a person approves what an agent proposes. The emerging pattern is a visible ledger of the agent's reads and claims, each claim linked to its evidence, and a shared working document rather than a chat log. *Fits:* Sentinel already has the boundary, the envelope, the stack and a subscribable handoff resource; what it lacks is making the agent's reads visible and letting a person and an agent build one investigation together.

## Three directions

Each differs in what the product *is* to a person: A is organised by the person's complaint, B by time, C by the investigation. All three keep the envelope's outcomes and evidence classes visibly distinct, keep exact rows one step from every summary, give every screen an agent equivalent through the API, and meet the brief's requirements (keyboard, screen reader, reduced motion, 44 px targets, 390 px phones, CSS before JavaScript). They were settled after an adversarial challenge and a parallel critique; [Challenge and revisions](#challenge-and-revisions) records what changed and why.

### A. Situations: the machine answered by what the person came with

**Thesis.** People arrive with a complaint, not a reading: *it stopped or restarted*, *it is slow*, *space is filling*, *the hardware is reporting errors*, *I want my agent to look*. The home screen is those doors, each carrying one observed fact with its time and outcome ("last unplanned stop 3 days ago", "6 hardware reports in the last minute", "not read"), never a score and never "fine". Behind each door is a fixed composition of existing readings in a set order: for a stop, `crash`, then the record before it, then `changes`, then hardware-error traffic around the moment. The same compositions are served to the agent as named recipes, so the person's door and the agent's call are one object.

- **Navigation.** Home (doors) → Situation (the composed evidence, in order) → exact record. Moving between doors is one step, because choosing a door must not commit anyone to a cause. Machine and Space stay as places; Diagnostics become the further readings a situation offers when its evidence runs out.
- **Home answers.** *Is there something here I should look at, and where do I start?* Each door states what was observed and when; an unread or failed input says so in its own shape, distinct from zero.
- **Visual language.** Keeps the dark instrument field and the phosphor and adds the missing semantic channel, used only where a door has evidence to point at: outcome states first (observed, zero, not read, failed, each distinct in word and shape), then two redundant levels of attention (word, glyph and hue together: the recorded amber `#FFB454` and a coral for a stop), never hue alone and never on a door with nothing behind it. Questions set in DM Sans at reading size; Azeret Mono with tabular figures only for the one number on a door; JetBrains Mono only for exact values. Depth from the existing raised surface and inspection well with the partitioning borders removed. Motion only when a door's fact changes.
- **Why it fits.** It takes the audit's first structural cause head on and answers the glance question (is anything wrong) with the product's honesty: an observed fact, its time and its coverage. It asks almost nothing new of the API, and it gives the agent the composed, stable-shaped summary it lacks today.
- **References.** Clinical practice more than clinical monitors: the presenting complaint that orders the examination. Sentinel's own `diagnostic-sweep` and `crash-forensics` agent procedures already work this way. Task Manager's small multiples for the door grid.
- **Risks.** A door names a category of complaint and can be read as a category of cause; the copy must stay in the person's words and every door must link to the others. Doors chosen because data exists become dashboardification. Asks the API for the compositions as named recipes (one route and one MCP prompt or tool each) and a cheap free-space figure outside the Space walk; everything else exists.

### B. Chart: the machine's record on one time axis

**Thesis.** The product is a record, and a record is read along time. Sentinel becomes a chart recorder of the machine: one shared time range, and every source as a track on it (stops, hardware error traffic, program faults, System-log density by level, updates and driver changes, performance samples, Windows' reliability days). The person sets the range once; selecting a moment or a stretch opens *the record around it* in an inspector beside the chart, without moving the chart. Each current view becomes either a track or an inspector lens on the selected moment.

- **Navigation.** The address is a range and a moment (the moment is already in the URL). Zoom from 30 days to a minute; the inspector holds the selection; Machine and Space remain places, reached from the rail, because they are about what the machine is rather than when.
- **Home answers.** *What happened, when, and what was read around it?* The default range is the last seven days with every stop marked and a one-line sentence per mark.
- **Coverage is drawn as prominently as data.** Each track shows its own reach (the rows `events` returned, the stops `crash` returned, the 48-hour performance window per request, the log's oldest retained record) as a band; outside it the track is hatched *not read*, never blank. A blank inside the band means the source was read and returned nothing there. Aligned emptiness across tracks is never presented as agreement. The inspector says *near*, never *because*.
- **Visual language.** A light theme for the first time, as David allowed: recording paper. Warm off-white field, a ruled time grid, tracks as ink, one exhibit red for stops and one ochre for hardware error traffic, with the dark instrument field kept as the dark appearance. Sans for text and mono only for times and exact values. Depth is flat by design, one raised sheet for the inspector. Motion: the cursor and range change in under 150 ms; nothing moves at rest.
- **The phone.** The phone is a vertical day list of the same marks with the same coverage bands, and it is canonical for the marks; the desktop chart adds the tracks between them. One model, two densities.
- **Why it fits.** *The record before this* is the product's signature mechanism; this direction makes it the whole interface. It is built on mechanisms that already exist: the moment in the address, the record before a moment, and buckets that carry their coverage (`storms` and `whea_reports` return null totals for unknown coverage). The reliability day strip already inside Crashes is its seed.
- **References.** Windows Reliability Monitor; the DevTools Performance panel; Grafana's shared time range and Honeycomb's selection comparison; paper chart recorders.
- **Risks.** An expert's instrument: a newcomer may see stripes, not an answer, so the home needs its sentences. Placing a stop on the axis means choosing which of its times is the mark; the stop's own evidence times (last record before restart, Windows' estimate, next start) should all be drawn, never collapsed. Asks the API for one `timeline` projection: per-source counts over one range with each source's coverage, event density by level (today `events` returns capped rows, not counts), fault buckets, and marks with their exact references. Several of those series exist today and would be composed rather than invented.

### C. Case file: an investigation a person keeps, with the agent proposing

**Thesis.** People come to Sentinel because something happened, and troubleshooting spans days and a conversation with an agent. The unit becomes the *case*: "it froze last night", opened from a stop, a lead or a question. A case gathers cited evidence (exact records, readings, the record before a moment), its own timeline, and notes. The agent does not write into a case; it *proposes*, the way a pull request proposes a change: a proposal carries its citations, arrives visibly as a proposal, and enters the case's evidence only when the person accepts it in the dashboard. The stack becomes a case's evidence and the handoff becomes the case exported.

- **Navigation.** Home → Case → Evidence. Home shows open cases, suggested starting points (stops and leads), and proposals waiting for review. A case has an evidence column, the case's timeline and the proposals; every reading is reachable from *Add evidence* as a lens rather than a destination. A case has a close state, so a case list does not grow forever.
- **Home answers.** *What am I looking into, what does the agent propose, and what did it read to propose it?*
- **Authorship stays honest.** Today one token opens every route, so the server cannot tell the person from an agent. Until each client has its own credential, the case shows the route an item arrived by (*accepted in the dashboard*, *proposed through the API*), never a claimed author. The proposal model makes that enough: nothing enters the evidence without a person's accept.
- **Visual language.** Editorial rather than instrumental: a serif display for case titles, sans for notes, mono only for citations and exact values. Each piece of evidence is an exhibit with a tag naming its reading, its class and when it was taken (the exhibit tag recorded in identity direction B). Proposals sit visibly apart from accepted evidence, as a review surface. Both appearances; the dark one keeps the green field. Motion: an accepted proposal settles into the evidence column with one brief highlight.
- **Why it fits.** It is the only direction that answers *what does my agent see* and gives the person a review step over the agent's work, which is the two-first-class-users promise made visible.
- **References.** Pull-request review; observability notebooks and incident timelines; Sentry's issue as the unit; clinical case notes.
- **Risks.** Nobody opens a case on a first visit, so its home must still answer the glance without one. The largest API ask by far: named cases with open and closed states replacing the one global stack, a proposal route with review, a record of what each proposal read, per-case storage with a real concurrency story (the stack today is one file behind a cross-process lock, and a damaged file answers 503 for the whole stack), and eventually a credential per client. It changes the security boundary and needs its own design pass before it is built beyond a synthetic prototype.

### Considered and set aside

- **Vitals: the machine as a patient on a monitor.** The first draft's direction A: a home of vital signs with trends, and episodes below. Set aside after challenge. A monitor's value is its alarm limits, and Sentinel cannot source a normal range, so vitals without limits become tiles. Trends need retained history the product keeps only for performance, and past hardware-error bursts are a label the API deliberately withholds (`storms` gives no burst status for a historical window; `whea_reports` refuses the word burst because of PreviousError). What survives is carried into A: one observed fact per door, the priority channel used only where there is evidence to point at, and a stable-shaped summary the agent can read.
- **Atlas of the machine** (a map of components with events pinned to parts). The Space lab shows how strong a spatial model can be, and the Machine map and PCIe groups point that way. Set aside as the whole product's model because most records cannot be attributed to one component without inferring it. It survives inside every direction as the Machine and Space places.

### Recommendation, provisional

Build all three as the brief asks; they are cheap to compare on the fixtures and they answer different questions. On the evidence so far, **B is the strongest model** (both reviewers ranked it first or second; it is the product's own mechanism made visible; its API ask is mostly composition), **A is the strongest first visit**, and **C is the right long-term shape for the agent** but the wrong first build. If David chooses B, A's doors are a natural home above the chart; that is his call, not an assumption the prototypes should make.

Open questions only David can answer: whether a light appearance is welcome as the default (B) or only as an option; whether the green instrument identity is a constraint or a starting point; whether the prompt presets with predictive names (*Preventative Oracle*, *Quantum Diagnostician*) should be renamed or removed, since agents receive them too.

## Challenge and revisions

The draft of this note was challenged before the directions were settled. Both reviewers received the draft; neither received anything from a real machine.

- **GPT-6 Sol** (`multithread peer codex`) was refused twice before submission: Multithread reported that its hooks were not ready for this checkout and must be reviewed in an interactive launch. The friction is recorded; no Sol review informs this note.
- **An independent Opus 5.5 review** (`multithread peer claude`, high effort, read-only, 158 seconds) stood in. It confirmed most of the audit against source and corrected four claims, now fixed above: Error and Critical glyphs differ (the near-collision is Error against Information); a reliability day strip does show time across sources, inside Crashes; Machine's ten items are jump links; the token set already has raised and inspection surfaces. It found the prompt-preset naming is an API defect, not only a screen one. It argued Vitals would collide with the evidence rules (no normal ranges, no retained trend, burst labels the API withholds) and proposed Situations in its place; it ranked B first for both users and C as a layer on B.
- **Buddy** (Muse, through the bridge, about ten minutes) returned a parallel critique. It ranked Vitals first, for its value to the agent as one stable-shaped summary, B second and C last, and named the risks the draft understated: priority levels with no episode to point at teach a person to ignore them; tracks with different ideas of a gap read as agreement; notes without an author field blur provenance. Its missed idea was the pull request: an agent's contribution should arrive as a proposal, visibly authored, accepted or rejected by the person.

**What changed.** Vitals became Situations, keeping Buddy's point (one stable-shaped summary the agent reads) and the Opus point (no normality metaphor, no invented trend). B gained coverage bands drawn as prominently as data, all of a stop's evidence times, and a canonical phone model. C adopted the proposal model and states authorship by route until each client has a credential. The two reviewers disagreed on the first direction; the disagreement is recorded rather than averaged.

## The harness

`docs/screens/fixtures/capture-views.cjs` renders any view or state at 1440x900 and 390x844 and saves a PNG per shot and width. The shots are a table in the script, so a direction adds a state there rather than writing another script. With the fixture server running as `docs/screens/README.md` describes:

```
NODE_PATH=<scratch>/node_modules TOKEN_FILE=<scratch>/token PORT=8021 OUT=<dir> FULL=1 \
  node docs/screens/fixtures/capture-views.cjs            # every shot
node docs/screens/fixtures/capture-views.cjs --list          # the shot names
node docs/screens/fixtures/capture-views.cjs crashes-open    # one shot
```

It reports each page's `scrollWidth` against the viewport, so horizontal overflow is caught at capture. `CHROMIUM` names a browser executable when Playwright's own download is missing. For this audit the fixture server gained three synthetic sources so every view renders something: the `crash` collector from `tests/fixtures/crash-records.json` (five sessions with stops, reports, dumps and the record before each start), the machine readings from the payloads `tests/test_system.py` asserts against, and six generically named processes. Reliability, PCIe, constraints, changes, performance history and Space still answer empty or failed, and the captures show that honestly. The captures here were reduced to 256-colour PNGs to keep the repository light.
